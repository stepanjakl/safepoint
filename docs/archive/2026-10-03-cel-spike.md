# Formula engine and sheet reader trials · 3 October 2026

Phase 0 of the [sheet process plan](../SHEET-PROCESS-PLAN.md). Both trials run
on demand from the Brunch weekend page in development (`/examples/avocado-toast`),
and the same functions run in the unit tests. Numbers below are from the trial
as run on 3 October 2026.

## Decision

**Adopt `@marcbachmann/cel-js` 8.0.0 as the formula engine.** Keep
`@bufbuild/cel` 0.6.1 as an independent cross-check in tests: every rule
example is evaluated by both libraries, and any disagreement fails the build.
Decided by the project owner after reviewing the results on the page.

Why cel-js, for rules a model drafts and a person approves:

- It type-checks a formula before running it, with the position of the error.
  That is the feedback the drafting loop returns to the model. Buf has a checker
  internally but does not export it, so its errors appear only at run time.
- Its departures from the specification are mostly strictness (it refuses
  mixed-type comparisons and lists), which suits typed money and stock rules.
  Where the specification absorbs an error (`missing || true` is `true`),
  cel-js raises it; for rules that fail closed, that is the safer behaviour.
- It enforces structural limits; Buf exposes none.
- Its syntax tree is reachable, for the labelled-formula rendering.
- It has no dependencies, an MIT licence, and runs in the browser.

Risks accepted: a small maintainer base, and a model trained on standard CEL
may write something cel-js rejects. The type check catches that immediately,
the adapter in `lib/rulebook/cel-engines.ts` keeps a switch to one file, and
the Buf cross-check flags any change in behaviour on an upgrade.

Traps: whole-number division stays whole (`7 / 2` is 3), whole and decimal
numbers are not mixed (`1 + 1.5` refused), a misspelt field is refused
(cel-js when checked, Buf only when run), a type error is refused (likewise),
and an oversized formula is refused (cel-js only).

## Corrections made during the trial

- The plan said `20 × 1.4` rounds wrongly in floating point. It does not.
  A real case is `50 × 1.1 = 55.00000000000001`, which rounds up to 56 instead
  of 55. The plan, the trial and the tests use that example now. None of the
  seeded rows happens to hit it.

## Sheet reader, so far

- A live read through Composio (`GOOGLESHEETS_BATCH_GET`, toolkit version
  `20261001_00`, pinned) returned all 10 tabs: 91 rows, 442 cells, 0 issues,
  in about 1.3 s. Tab ids came from `GOOGLESHEETS_GET_SPREADSHEET_INFO` in
  about 1.1 s; they make the cell links on the page work.
- Composio rejects a bare tab name that also reads as a column reference
  (`Kit`), so every tab is requested with an explicit range (`Kit!A1:Z200`).
- Money arrives in pounds and becomes whole pence; times arrive as a fraction
  of a day and become minutes after midnight (`0.3645833333333333` is 08:45);
  columns are found by header, so a moved column still binds and a renamed one
  is reported.
- Run timing: weekdays and times resolve to instants for a pinned run time
  (observations to their latest occurrence, deadlines inside the planned week),
  with real hours across both clock changes. Tested for every run time in the
  plan's table and shown in the Calculate step.
