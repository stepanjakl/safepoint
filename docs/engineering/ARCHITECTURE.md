# Architecture

Status: current implementation guide, checked against the repository in November 2026, after the move of runs, rulebooks and jobs to the server. The [original technical design](../archive/TECHNICAL-DESIGN.md) contains a fuller proposed production system; it is a dated design record, not a claim that those services exist.

## Implemented boundaries

The Next.js App Router serves a shared process shell. `lib/shell/routes.ts` maps process summaries to their pages. `components/app-shell/` owns navigation, tabs, runs and thread layout; `components/engine/` holds the screens a process with a rulebook is worked through (rules, calculate, propose, apply), which serve any such process; Both Brunch orders processes are in the navigation and served wherever the gate applies, deployed or local. The development tools (`/workbench`, `app/api/dev/`, `components/dev/`) check for local development before use and answer not found elsewhere.

Brunch orders is the active development process. `lib/processes/brunch-orders/` declares its subject, five data tabs and versioned instructions, and `components/processes/brunch-orders/` holds its two run screens (`/processes/brunch-orders` and `/processes/brunch-orders-direct`; the old `/examples/…` addresses redirect permanently, `lib/shell/moved-routes.ts`); a read is captured or fetched through Composio and kept under an ID. `lib/engine/` finds definitions, checks formulas and examples, and stores the person's accepted definitions by instructions hash. The current flow is described in the [definitions engine guide](DEFINITIONS-ENGINE.md).

A process's data lives in **sources**, kept apart from what the process does with them. `lib/sources/model.ts` declares each source (a Google spreadsheet today, in code until sources can be added in the app) and its kind's vocabulary; a source knows its resources (a sheet's tabs), their rows and their columns, and nothing of any process. A process names only the resources it reads and writes (`SourceUse`, for Brunch orders `SHEET_USE`); a resource may be in both lists, and what it means to the process stays in its `DataShape`. Reading a source from its own page (`server/storage/source-reads.ts`, through the `sources` procedures in `server/api/routers/sources.ts`) keeps every tab whole in the `source_reads` table; until the first such read the captured snapshot stands in. This is separate from a run's read, which the run takes and keeps for itself. The Outputs tab's last write comes from the process's kept writes (`lastWrite` in `server/storage/applications.ts`). The screens are `components/app-shell/sources/`.

The models the app may call are listed in `lib/models.ts`; typed sheet cells and the week arithmetic they use are in `lib/sheets/`. The earlier Brunch weekend experiment, which these grew out of, was removed on 13 October 2026. The earlier promotion-release prototype (its replay review, evidence, policy and model workbenches) was removed too and can be recovered from the git tag `archive/promotion-prototype`.

## Where things live

- `app/`: routes and pages (`(shell)/` the app, `workbench/` the development laboratories, `api/trpc` the one stateful door, `api/dev` the plain development routes, `access/` the password page), and `styles/`, the one stylesheet entry.
- `components/`: `app-shell/` (the shell, by feature), `engine/` (the generic rulebook, calculate, propose and apply screens, which import nothing of a process and take its subject as props), `processes/<process>/` (the run screens of one process, which own what is specific to it and hand it to the engine screens), `ui/` (controls), `trpc/` (the client's provider), `access/` and `dev/`.
- `lib/`: code that runs on either side and holds no state. `engine/` is the rules engine (kept flat, one file a concern); `shell/` the process model, navigation, routes and the plan contract that feeds the menu's status; `processes/<process>/` everything that defines one process (`process.ts` its ids, instructions, summaries and plans; `data.ts` the sheet it reads and its subject; `steps.ts` the steps of a run; `types.ts` beside them the shapes every process declares); `sources/` and `sheets/` the data a process reads and writes.
- `server/`: everything that touches the database, a file, a model or a sheet, each module opening with `import 'server-only'`. `api/` the procedures, `storage/` where each kind of thing is kept and read back (`run-reads.ts` a run's read), `operations/kept-processes.ts` the one registry that maps a process id to its declaration, evaluation and where its data is read from (the only server module that imports `lib/processes`; ESLint holds the line), `jobs/` and `workflows/` the background work, `operations/` what a procedure does across several stores, `access/` the gate, `db/` the schema and client.
- `drizzle/`: the migrations. `fixtures/`: the reviewed copy of what a person approves (`<process>/rulebooks/`, `<process>/profile/`), and the captured sheet read. `e2e/`: browser tests and their frozen copies. `scripts/` and `tools/`: generators and structural checks. `data/` (ignored): what runs write locally with no `DATABASE_URL`.

## How a route becomes a procedure

The client reaches the server through tRPC procedures served at `/api/trpc/<router>.<procedure>` (`app/api/trpc/[trpc]/route.ts`), read and cached by TanStack Query. Every call is a POST with its input as the JSON body, queries too (`methodOverride: 'POST'` on the client's link, `allowMethodOverride: true` on the handler): an input can be as long as a process's instructions, which a URL cannot carry and a log should not keep. To TanStack a query is still a query. The sources panels were the first, and every stateful route since has moved across; what stays under `app/api/dev/` are the plain development routes (class origins, stylesheets, the test proposal).

- **Where it goes.** One router per area in `server/api/routers/<area>.ts`, merged into `appRouter` in `server/api/root.ts`. tRPC reserves `apply`, `call` and `then` as names, so the Apply step's router is `application`. A procedure calls the same functions in `server/storage/`, `server/jobs/` or `server/operations/` the route called; it holds no logic of its own beyond refusing what it cannot serve.
- **The gate.** Every stateful procedure starts from `gatedProcedure` (`server/api/trpc.ts`): in local development a loopback host and no foreign origin, refused as `NOT_FOUND` or `FORBIDDEN`; wherever the shared-password gate applies, a valid gate cookie and no foreign origin, refused as `UNAUTHORIZED`, `SERVICE_UNAVAILABLE` or `FORBIDDEN`. The checks are `localDevelopmentRefusal`, `gateApplies` and `crossOriginRefusal` in `lib/dev/dev-route.ts`, shared with the plain routes that remain. Who may call is decided there and nowhere else.
- **Inputs.** The route's Zod schema moves to `.input()` unchanged, one procedure per `action`. A read is a `.query()`; anything that keeps, writes or spends is a `.mutation()`.
- **Errors.** Throw `TRPCError` with the code the route's status meant (404 `NOT_FOUND`, 409 `CONFLICT`, 502 `BAD_GATEWAY`) and the route's own message. The error formatter in `server/api/trpc.ts` sends the first line of any message and "Invalid request." for an input tRPC refused, so neither a stack nor a Zod issue list reaches the screen. On the client, `error.message` is that text.
- **Reading.** In a client component, `const trpc = useTRPC()` (`components/trpc/provider.tsx`), then `useQuery(trpc.<area>.<name>.queryOptions(input, options))`, or `useQueries` for several. Data the server page already loaded goes in as `initialData` with `staleTime: Infinity` when nothing else changes it, and is then never fetched. A read made on an event (opening a drawer) is `queryClient.fetchQuery(trpc.<area>.<name>.queryOptions(input))`.
- **Writing.** `useMutation(trpc.<area>.<name>.mutationOptions({ onSuccess }))`, where `onSuccess` writes the answer into the queries it changes (`queryClient.setQueryData(trpc.<area>.<other>.queryKey(input), data)`) or invalidates them (`invalidateQueries(trpc.<area>.pathFilter())`). Its pending and failed state, seen from any component, is `useMutationState({ filters: { mutationKey: trpc.<area>.<name>.mutationKey() } })`. `components/app-shell/sources/source-queries.ts` is the pattern.
- **Defaults.** No refetch on focus, no retry of a query or a mutation, a 30-second stale time; reasons in `components/trpc/provider.tsx`. Polling is a query's `refetchInterval`, not an interval of its own. No data transformer: dates are ISO strings.
- **Testing a procedure.** `appRouter.createCaller({ request: new Request('http://localhost:3000/api/trpc') })` calls it in process, with `vi.stubEnv('NODE_ENV', 'development')` for the gate and `inScratchDirectory()` for files (`server/api/routers/sources.test.ts`). A caller throws the raw `TRPCError`; what reaches the screen is tested by calling the handler's `POST` with a `Request` (`app/api/trpc/[trpc]/route.test.ts`).
- **Mocking one in a browser test.** `mockProcedure(page, '<area>.<name>', { data } | { error: { code, message } } | (input) => …)` from `e2e/trpc.ts` answers in tRPC's wire format, typed from the router, and returns `{ inputs }`, what the page sent (read from the POST body, whatever the procedure's type). The client's link is unbatched so each procedure has its own URL; keep it so.
- **A run's procedures.** A procedure about a run's read and rulebook starts from `runProcedure(input)` (`server/api/run-procedure.ts`) in place of `gatedProcedure.input(input)`: the context carries `process` (the registry's entry for the run's process, picked from the input's `evaluation` or the kept run), `read`, `owner`, `set`, `current` (the rulebook current for the instructions), `pinned` (whether `set` is the revision the run named, kept as accepted), `stale` and `published`, as `rulebookFor` (`server/operations/run-rulebook.ts`) works them out for that process. The procedures whose inputs name no process (`rules`, `calculate`, `read`) work on `rulebookProcess()` from the same registry. A rulebook that no longer fits the read is not an error: the screen renders what does not fit, so the handler begins `if (ctx.stale) return staleReply(ctx.stale)` and the output is a union with `{ kind: 'stale', … }`, which keeps the state in the query's data beside the last good answer. Anything else that goes wrong while working is a `BAD_GATEWAY` with its own message, as the routes answered.
- **Rules and Apply.** The `rules` procedures work on the instructions' text and a read id that may be absent, so they do not use `runProcedure`; they share a small `rulesProcedure` that answers a thrown error as a `BAD_GATEWAY` with its own message. `get`, `debug` and `debugDraft` are queries (reads of kept state); every other action is a mutation, `advise` too, as it asks a model. All but `advise`, `debug` and `debugDraft` answer with the rules as they stand, which the Rules step writes into every `rules.get` entry for its text, so the rulebook panel and its history show a decision as it is made. `application.preview`, `write` and `undo` all reach the sheet, so all three are mutations, which the client never retries. A write the sheet's state refuses answers with the preview that says why; an undo that cannot be done is a `CONFLICT`.
- **Jobs and polling.** A procedure that starts a job is a mutation, and writes the answer it gets into the query that reads the job (`setQueryData`). That query polls with `refetchInterval` as a function of its data, `false` once the job is not running. The job itself (a draft, a rewrite of one rule, a proposal) is a Vercel Workflow run (`server/workflows/`, started through `server/jobs/`): each unit of model work is a step whose result the run keeps, so a restart or a redeploy carries it on from the last finished step; its progress is the `jobs` row the query reads, and whether one kept as running is running is its run's status ([Database](DATABASE.md), "Jobs"). A workflow function only orchestrates; a step loads its work by dynamic import, since the workflow's sandbox cannot load the database driver. Locally the Local World keeps runs in `.next/workflow-data/` and `instrumentation.ts` starts it, which carries on the runs a stopped `pnpm dev` left; deploying is in the [README](../../README.md#deploying-to-vercel). `useMutationTrial` (`components/engine/trial-parts.tsx`) gives a mutation the state `TrialControl` shows.
- **Then** delete the route, move its client types to inference (`inferRouterOutputs<AppRouter>` where a name is needed), and update this guide and `AGENTS.md` if a path they name moved.

## Trust and state

- The model can propose definitions or changes. Code validates its output; a person accepts a definition. Model tools do not own external write authority.
- Captured snapshots and fixtures allow local work without credentials. Live sheet reads require the development Composio configuration.
- What runs produce (reads, cross-checks, drafts, proposals, writes to a sheet) is kept server-side: reads, a source's reads, proposals, cross-checks and their partial answers, the progress of drafts and proposals as background jobs, the record of each write to a sheet (`applications`), each model request (`model_attempts`) and learned model limits in the database ([Database](DATABASE.md)). The server also keeps runs, each decision on a proposal as an event, and the instruction versions a person publishes, labelled by the server (`runs`, `decisions` and `instructions` procedures); the screens read and write them there, and a write takes its decisions from there (`application.*` names a run by `{ process, runId }`), so they survive a cleared browser and appear in another one ([Runs on the server](RUNS-ON-THE-SERVER.md)). How far a run's rules, calculate, propose and apply steps have got is not kept: each step works it out again from what it summarises as it opens. Rulebooks and data profiles are in the database too, through `server/storage/rulebooks.ts`, their only door: per instructions version (by the hash of its text) the rulebook under review (`current_rulebooks`), each accepted revision kept unchanged so a run can return to it (`rulebook_revisions`, by its fingerprint, with its parent and reason) and the head (`rulebook_heads`); per process the profile under review and each confirmed one. Each act on a rule is also a `rule_decisions` row. Each revision is re-checked against the read it is used on. What a person approves stays reviewed in git as `fixtures/<process>/rulebooks/<version>-<instructions hash>/` (`current.json`, `<rulebook id>.json`, `revisions.json`) and `fixtures/<process>/profile/`: a database that lacks them is seeded from there on first need, and `pnpm rulebooks:export` writes the database's state back, byte for byte (`server/storage/rulebook-files.ts`, the only code that reads or writes those files). [Database](DATABASE.md) maps every kept file and browser store to its table and says what the database enforces.
- Who may use the app outside local development is one shared password (`server/access/`). Local development (`NODE_ENV=development` on a loopback host, the judgement `lib/dev/dev-route.ts` keeps for the development-only tools too) has no gate and needs no configuration; `SAFEPOINT_GATE=1` applies the gate there as well, to try it. Elsewhere `SAFEPOINT_ACCESS_KEY` and `SAFEPOINT_COOKIE_SECRET` must both be set and long enough, or every request is refused as not configured: the gate never falls open. A person gives the password and a name on `/access` and holds both in an HMAC-SHA-256 signed cookie (`HttpOnly`, `SameSite=Lax`, `Secure` outside local development, 30 days counted from the signed issue time). The request proxy (`proxy.ts`, decisions in `server/access/decision.ts`) sends a page without a valid cookie to `/access` with a same-origin return path, and answers an API call with 401 JSON. `/_next/`, `/icon.svg` and Vercel Workflow's `/.well-known/workflow/` stay open. `gatedProcedure` checks the cookie again itself, so no procedure depends on the proxy having run, and `ctx.actor` is the cookie's name, written on each decision. The development-only tools never read the cookie or the gate switch: they refuse outside local development whoever is signed in. What this is not: there are no accounts or roles, the name is self-declared and not verified, and attempts are not throttled, so the password must be long and random. Changing `SAFEPOINT_COOKIE_SECRET` (or the cookie's version in `session.ts`) signs everyone out; that is how to rotate.
- The app is built to be served beyond a developer's machine, on Vercel, behind that gate. Every page and `/api/trpc` needs the cookie; the two Brunch orders processes are in the navigation and open like any other; the development tools answer not found even when signed in (`/workbench` pages call `notFound()` outside development, `app/api/dev/` routes call `rejectUnlessLocalDevelopment`, and the dev-only components render nothing). Production-mode behaviour was checked locally with `next start` under `NODE_ENV=production`, the gate configured, PGlite in a scratch folder, no model key and the captured read: a run starts, reads the captured sheet, shows the rulebook seeded from `fixtures/` and calculates; proposing and the cross-check stop at the model call. Four things differ from development. With no `DATABASE_URL` on Vercel (`VERCEL` set) `database()` is an error, never PGlite on a read-only disk. The production build, `vercel-build` (`scripts/vercel-build.ts`), applies migrations over the direct connection first, and only when `VERCEL_ENV=production`. The pool is released before an idle function is suspended (`attachDatabasePool`). And the files read by path at run time, `fixtures/brunch-orders/`, are named in `next.config.ts` (`outputFileTracingIncludes`) for the routes that reach them, since Vercel bundles only what a trace lists. The cross-origin check compares `Origin` with `request.url`, which on Vercel Next forms from the `Host` header (it trusts it when built there), so it needs no forwarded headers. The tRPC route asks for `maxDuration = 300`, the most a Hobby plan allows, because two procedures (`calculate.crossCheck`, `rules.advise`) ask a model inside the request. The deployment checklist is in the [README](../../README.md#deploying-to-vercel).
- The proposal review in Brunch orders illustrates proposal accounting and inspection. Approval and execution of external effects are not implemented as a production flow.

## Proposed production architecture

The portfolio direction calls for server-authoritative review revisions, durable persistence, bounded model generation, application-owned adapters, preflight checks, verified writes, an effects ledger and compensation where safe. Those are proposed capabilities in the [archived technical design](../archive/TECHNICAL-DESIGN.md) and [delivery plan](../archive/DELIVERY-PLAN.md). The active [Brunch orders plan](../processes/brunch-orders/PLAN.md) gives the present sequence for calculation, proposal, checking, review, application and history; each phase must be checked against code when built.
