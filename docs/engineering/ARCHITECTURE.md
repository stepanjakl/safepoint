# Architecture

Status: current implementation guide, checked against the repository in October 2026. The [original technical design](../archive/TECHNICAL-DESIGN.md) contains a fuller proposed production system; it is a dated design record, not a claim that those services exist.

## Implemented boundaries

The Next.js App Router serves a shared process shell. `lib/process/routes.ts` maps process summaries to their pages. `components/app-shell/` owns navigation, tabs, runs and thread layout; `components/review/` renders the shared review presentation. Development-only process and model routes check for local development before use.

The promotion-release example loads validated fictional evidence and a reviewed replay through `lib/promotion-release/`. `lib/review/` adapts that replay into the shared release-plan presentation. The replay item API loads details on demand. A preview review surface is not evidence of an external write.

Brunch orders is the active development process. `lib/processes/brunch-orders/` declares its subject, five data tabs and versioned instructions; a read is captured or fetched through Composio and kept under an ID. `lib/definitions/` finds definitions, checks formulas and examples, and stores the person's accepted definitions by instructions hash. The current flow is described in the [definitions engine guide](DEFINITIONS-ENGINE.md).

A process's data lives in **sources**, kept apart from what the process does with them. `lib/sources/model.ts` declares each source (a Google spreadsheet today, in code until sources can be added in the app) and its kind's vocabulary; a source knows its resources (a sheet's tabs), their rows and their columns, and nothing of any process. A process names only the resources it reads and writes (`SourceUse`, for Brunch orders `SHEET_USE`); a resource may be in both lists, and what it means to the process stays in its `DataShape`. Reading a source from its own page (`server/storage/source-reads.ts`, through the `sources` procedures in `server/api/routers/sources.ts`) keeps every tab whole under `data/sources/<id>/reads/`; until the first such read the captured snapshot stands in. This is separate from a run's read, which the run takes and keeps for itself. The Outputs tab's last write comes from the process's kept writes (`lastWrite` in `server/storage/applications.ts`). The screens are `components/app-shell/sources/`.

The models the app may call are listed in `lib/models.ts`; typed sheet cells and the week arithmetic they use are in `lib/sheets/`. The earlier Brunch weekend experiment, which these grew out of, was removed on 13 October 2026.

## How a route becomes a procedure

The client reaches the server through tRPC procedures served at `/api/trpc/<router>.<procedure>` (`app/api/trpc/[trpc]/route.ts`), read and cached by TanStack Query. The sources panels were the first; the routes under `app/api/dev/` move across one at a time.

- **Where it goes.** One router per area in `server/api/routers/<area>.ts`, merged into `appRouter` in `server/api/root.ts`. A procedure calls the same functions in `server/storage/`, `server/jobs/` or `server/operations/` the route called; it holds no logic of its own beyond refusing what it cannot serve.
- **The gate.** Every stateful procedure starts from `gatedProcedure` (`server/api/trpc.ts`): local development, a loopback host, no foreign origin, refused as `NOT_FOUND` or `FORBIDDEN`. The checks themselves are `localDevelopmentRefusal` in `lib/dev/dev-route.ts`, shared with the plain routes that remain. Who may call is decided there and nowhere else.
- **Inputs.** The route's Zod schema moves to `.input()` unchanged, one procedure per `action`. A read is a `.query()`; anything that keeps, writes or spends is a `.mutation()`.
- **Errors.** Throw `TRPCError` with the code the route's status meant (404 `NOT_FOUND`, 409 `CONFLICT`, 502 `BAD_GATEWAY`) and the route's own message. The error formatter in `server/api/trpc.ts` sends the first line of any message and "Invalid request." for an input tRPC refused, so neither a stack nor a Zod issue list reaches the screen. On the client, `error.message` is that text.
- **Reading.** In a client component, `const trpc = useTRPC()` (`components/trpc/provider.tsx`), then `useQuery(trpc.<area>.<name>.queryOptions(input, options))`, or `useQueries` for several. Data the server page already loaded goes in as `initialData` with `staleTime: Infinity` when nothing else changes it, and is then never fetched. A read made on an event (opening a drawer) is `queryClient.fetchQuery(trpc.<area>.<name>.queryOptions(input))`.
- **Writing.** `useMutation(trpc.<area>.<name>.mutationOptions({ onSuccess }))`, where `onSuccess` writes the answer into the queries it changes (`queryClient.setQueryData(trpc.<area>.<other>.queryKey(input), data)`) or invalidates them (`invalidateQueries(trpc.<area>.pathFilter())`). Its pending and failed state, seen from any component, is `useMutationState({ filters: { mutationKey: trpc.<area>.<name>.mutationKey() } })`. `components/app-shell/sources/source-queries.ts` is the pattern.
- **Defaults.** No refetch on focus, no retry of a query or a mutation, a 30-second stale time; reasons in `components/trpc/provider.tsx`. Polling is a query's `refetchInterval`, not an interval of its own. No data transformer: dates are ISO strings.
- **Testing a procedure.** `appRouter.createCaller({ request: new Request('http://localhost:3000/api/trpc') })` calls it in process, with `vi.stubEnv('NODE_ENV', 'development')` for the gate and `inScratchDirectory()` for files (`server/api/routers/sources.test.ts`). A caller throws the raw `TRPCError`; what reaches the screen is tested by calling the handler's `GET` or `POST` with a `Request` (`app/api/trpc/[trpc]/route.test.ts`).
- **Mocking one in a browser test.** `mockProcedure(page, '<area>.<name>', { data } | { error: { code, message } } | (input) => …)` from `e2e/trpc.ts` answers in tRPC's wire format, typed from the router, and returns `{ inputs }`, what the page sent. The client's link is unbatched so each procedure has its own URL; keep it so.
- **Then** delete the route, move its client types to inference (`inferRouterOutputs<AppRouter>` where a name is needed), and update this guide and `AGENTS.md` if a path they name moved.

## Trust and state

- The model can propose definitions or changes. Code validates its output; a person accepts a definition. Model tools do not own external write authority.
- Captured snapshots and replay fixtures allow local work without credentials. Live sheet reads require the development Composio configuration.
- What runs produce (reads, cross-checks, drafts, proposals, writes to a sheet) is kept server-side under `data/<process>/` (gitignored); a run's own state, including a person's decisions on a proposal, is browser-local. Rulebooks are JSON under `fixtures/<process>/rulebooks/<version>-<instructions hash>/`: the one under review (`current.json`), each accepted revision kept unchanged so a run can return to it, and `revisions.json`, each revision's parent and reason and the head. Each revision is re-checked against the read it is used on. This is development storage, not a durable multi-user review database; `server/storage/rulebooks.ts` is its only door, shaped for the tables that replace it: a revision is a `rulebook_revisions` row (body as JSON, parent, reason, time, shape version), the head a `rulebook_heads` row per instructions version, and each acceptance or denial later an append-only decision event. In that world only the frozen copies the browser tests serve (`e2e/fixtures/`) stay in git.
- The existing review illustrates proposal accounting and inspection. Approval and execution of external effects are not implemented as a production flow.

## Proposed production architecture

The portfolio direction calls for server-authoritative review revisions, durable persistence, bounded model generation, application-owned adapters, preflight checks, verified writes, an effects ledger and compensation where safe. Those are proposed capabilities in the [archived technical design](../archive/TECHNICAL-DESIGN.md) and [delivery plan](../archive/DELIVERY-PLAN.md). The active [Brunch orders plan](../processes/brunch-orders/PLAN.md) gives the present sequence for calculation, proposal, checking, review, application and history; each phase must be checked against code when built.
