# Database

Status: designed and migrated; in use for a run's reads, a source's reads and learned model limits (batch 4a), for proposals, cross-checks, their partial answers and job progress (batch 4b), for the record of each write to a sheet and each model request (batch 4c), on the server side for instruction versions, runs and each decision on a proposal (batch 5a: the procedures are built, the screens move onto them in 5b, [Runs on the server](RUNS-ON-THE-SERVER.md)), and for rulebooks, data profiles and rule decisions (phase 6, "Rulebooks and profiles, as built", below), with `fixtures/` kept as their reviewed copy in git. Written 14 November 2026, updated 16 November. `server/db/` holds the client, the schema and its tests; `drizzle/` holds the migrations. Every kind is read and written through `database()` with no file fallback; the only files the server still reads are the captured sheet read and, for seeding and the export, `fixtures/`. With no `DATABASE_URL` the app opens PGlite under `data/pglite/` on the first request that needs it; tests use `inScratchDatabase()`, and `database()` refuses a test that has not set one up.

## Opening it

`database()` in `server/db/client.ts` is the only way in. It chooses once per server process, holds the result on `globalThis` (as `lib/definitions/limits.ts` holds the model limits), and connects only when first asked:

| Where          | Driver                                                        | Why                                                                                                                                                                                                                  |
| -------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL` | node-postgres `Pool`, 5 connections, idle 10 s, timeout 10 s  | Interactive transactions need a connection; Fluid compute reuses an instance. Use Neon's pooled URL (`-pooler`). Each setting's reason is in `poolFor`.                                                              |
| No URL         | PGlite on disk, `data/pglite/`, migrated on first use         | The app starts with no credentials (the README's promise, CI's browser job). A development dependency, loaded by dynamic import only on this path.                                                                   |
| Tests          | PGlite in memory, one per test file (`inScratchDatabase()`)   | No network, no files. Migrated once per test file and emptied before each test (`truncate … restart identity`): about 10 ms, against 150 ms to copy a migrated one (`clone()`) and 600 ms to create and migrate one. |
| Browser tests  | PGlite under `data/pglite-e2e/`, cleared as the server starts | `playwright.config.ts` starts `pnpm dev` with `DATABASE_URL` and `DATABASE_URL_UNPOOLED` empty and `SAFEPOINT_PGLITE_DIR=data/pglite-e2e`. See below.                                                                |

`SAFEPOINT_PGLITE_DIR` moves the PGlite folder (relative to the working directory); `driverFor` takes an empty URL as none, as `||` does. The browser tests' server gets both URLs empty because Next does not take a variable that is already set, an empty one included, from `.env.local` (`@next/env` uses a file's value only where the starting environment has none; checked with an empty `DATABASE_URL` and a `.env.local` naming one), so a developer's remote `DATABASE_URL` never meets a test row; and it gets a folder of its own, so a run does not write into the developer's `data/pglite/`. The server's start command removes that folder, so each run begins empty. `reuseExistingServer` is on outside CI: a server already on the port is used as it is, whatever database it has, and only the one the config starts is kept off a remote database.

Opened on the first request that asks, not at start: creating and migrating `data/pglite/` measured about 1.5 s (reopening it 0.7 s) including Node's own start, against 30 s browser-test timeouts, and requests arriving together share one open (`database()` stores the promise before awaiting it; `client.test.ts` holds it). The first request of a fresh `pnpm dev` took about 5 s, mostly the route's compile.

Storage functions take a `Database`, which a Drizzle transaction also is, so a caller can run one inside its own `db.transaction(...)`. Plain SQL's result type depends on the driver; prefer the query builder.

```sh
pnpm db:generate   # a migration from server/db/schema.ts; review the SQL, commit it
pnpm db:migrate    # applies drizzle/ to DATABASE_URL_UNPOOLED, DATABASE_URL, or data/pglite
pnpm db:reset      # drops everything and migrates; refuses any target not marked (below)
pnpm db:studio     # migrates, then browses it; not while pnpm dev holds data/pglite
```

Migrations run over the direct connection (`DATABASE_URL_UNPOOLED`): Neon's pooler is PgBouncer in transaction mode, which a migration's session state does not survive. In production they are to run in the Vercel build, production only; that step is not wired yet. `db:reset` refuses on Vercel and under `NODE_ENV=production`, and on any server unless `SAFEPOINT_RESETTABLE_DATABASE_URL` is that exact URL. Every module in `server/` begins with `import 'server-only'`, which throws outside a React server build; the scripts run Node and drizzle-kit with `--conditions=react-server`, under which the package resolves to its empty module, as Vitest's alias does.

### The locks on a real PostgreSQL

```sh
SAFEPOINT_TEST_DATABASE_URL='<a direct, unpooled URL>' pnpm test:postgres
```

PGlite runs one transaction at a time, so the suite cannot prove a lock. `pnpm test:postgres` runs `server/db/postgres.test.ts` against a real server through a node-postgres pool: two callers fired together hold two connections, and each race (labels, a write's claim, settling, undo, a decision racing a write, duplicate decisions, keeping a read or a proposal twice, and a job's lease, from two Node processes) runs 25 times (`SAFEPOINT_TEST_REPEATS` for more). Without the variable those tests skip, and `pnpm test` needs no server. Each test file creates a schema of its own, `safepoint_test_<12 hex>`, applies `drizzle/` into it with every `"public".` rewritten to it (`server/db/postgres.fixture.ts`; `postgres-schema.test.ts` proves the rewrite on every run), gives its connections that schema alone as `search_path`, compares `public`'s tables and row counts before and after, and drops its schema when it ends, failed or not. A process killed mid-run leaves its schema behind: drop any `safepoint_test_*` schema no run is using. It refuses a pooled URL (a search path does not survive PgBouncer's transaction mode) and production, and it is never pointed at the production database. Advisory locks are database-wide, so a run may wait briefly on one the development app holds. Every lock the storage code takes is transaction-scoped (`pg_advisory_xact_lock`), or a single guarded statement, so each holds through the pooler.

`drizzle/0000_tables.sql` is generated. `drizzle/0002_source_reads_latest.sql` adds the one index a query needed beyond the keys. `drizzle/0003_run_data_reads.sql` gives `proposals`, `cross_checks` and `answer_parts` their `read_process` and its key to `reads` (they were empty in every database, so the column is added not null). `drizzle/0004_write_leases.sql` does the same for `applications` (its key to `reads` was on `(process, read_id)`, wrong for the direct process; the table was empty everywhere), adds the lease a write or an undo holds on its row (`holder`, `heartbeat_at`, both or neither) and `model_attempts.requests` and `waited_ms`. `drizzle/0005_application_guard.sql`, by hand, replaces the `applications` guard so that `read_process` is among what never changes. `drizzle/0006_kept_runs.sql` fits `runs` to what a run is ("Runs, decisions and instruction versions, as built", below; the table was empty everywhere, so `read_process` is added not null), and `drizzle/0007_run_guard.sql`, by hand, is its guard. `drizzle/0008_job_runs.sql` adds `jobs.run_id`, the Workflow run a job is ("Jobs", below). `drizzle/0001_guards.sql` is written by hand (`drizzle-kit generate --custom`): drizzle-kit cannot write functions or triggers and keeps no record of them, so regenerating neither drops nor repeats it, and `server/db/schema.test.ts` fails if a guard is missing.

## Tables

Every table carries its scope: `process` (a key into `processes`), except `source_reads` (by `source`: a source knows no process) and `model_limits` (a quota is the API key's). A future workspace or session is an attribute of a `processes` row, not a column on every key: a process belongs to one workspace, the same template in two workspaces is two process ids, and no key or foreign key changes.

| Table                  | Holds                                                                                                         | Key                                                                   |
| ---------------------- | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `processes`            | The scope                                                                                                     | `id`                                                                  |
| `instruction_versions` | Each version's text, label, note, who and when; written once                                                  | `(process, hash)`; `version` unique; `hash` checked against the text  |
| `reads`                | A run's read, whole; written once                                                                             | `(process, id)`                                                       |
| `source_reads`         | A source's own read, every resource; written once                                                             | `(source, read_id)`                                                   |
| `data_profiles`        | Each confirmed profile; written once                                                                          | `(process, id)`, the `profileFingerprint`                             |
| `current_profiles`     | The profile under review, with a compare-and-set `revision`                                                   | `process`                                                             |
| `current_rulebooks`    | The rulebook under review per instructions, with a compare-and-set `revision`                                 | `(process, instructions_hash)`                                        |
| `rulebook_revisions`   | Each accepted rulebook: body, parent, reason, time, shape version, note, profile; written once                | `(process, instructions_hash, id)`, the `fingerprintOf`; `seq` orders |
| `rulebook_heads`       | The revision in use per instructions                                                                          | `(process, instructions_hash)`                                        |
| `runs`                 | Instructions (a key), read (a key, two scopes), pinned rulebook, stage, status, trigger, who, when, discarded | `(process, id)`; never removed                                        |

| `cross_checks`         | The model's cross-check by run key; replaced on a new check                                                   | `(process, read_id, fingerprint)`                                     |
| `answer_parts`         | A proposal or cross-check still being answered (the old `.part` files); replaced per batch                    | `(process, kind, read_id, fingerprint)`                               |
| `record_decisions`     | Approve, change (with values), reject or withdraw, on one record of one proposal, in one run                  | `id`; appended only                                                   |
| `rule_decisions`       | Confirm intent, accept, deny (note), choose (version), applies to, confirm profile                            | `id`; appended only                                                   |
| `applications`         | A write and its undo: status, range, before, after, changes, decisions, undo marker                           | `id`; one standing per run key                                        |
| `jobs`                 | A job's progress as columns, its holder and lease                                                             | `(process, kind, key)`                                                |
| `model_limits`         | Per model: shared quota, learned limits, today's count                                                        | `model`                                                               |
| `model_attempts`       | One model call: purpose, model, what it was part of, outcome, duration, tokens, summaries                     | `id`                                                                  |

Every foreign key restricts deletes; nothing cascades. A decision points at the exact proposal row it was made on, and a rule decision keeps the definition as it was shown and the rulebook's `revision` it was read at, so what was approved stays readable after the rulebook moves on. A profile's and a rulebook's `read_id` are not keys: the reads they came from are run data, and a database seeded from `fixtures/` has none. A proposal, a cross-check and a part have two scopes: `process`, the one the row belongs to and which stays in every key, and `read_process`, the one whose read it was made on, with a foreign key `(read_process, read_id) → reads (process, id)` that restricts deletes. They differ for Brunch orders' direct process (`brunch-orders-direct`), which proposes on reads kept under `brunch-orders` (4 of the 8 proposals in the owner's data are its), so a key on `(process, read_id)` was wrong for it. `readProcessOf` in `server/storage/brunch-orders-reads.ts` is the one place that says which process keeps a process's reads; `keptRead` and the writes of these three kinds both use it, so they cannot disagree. A proposal for a read that is not kept is refused by the database, and the import says why first. The later `runs → reads` key takes the same `read_process` shape. A proposal's fingerprint is not a key either: a process with no rulebook proposes under the empty rulebook's (`noRules`).

Stay in the browser: the unpublished instructions draft (now `safepoint.instructions.v3`, `{ [process]: { draft } }`; a v2 draft is read once, where v3 holds none for the process), and the preferences and previews (`assistant`, `calculate-revealed`, `inputs`, `last-process`, `process-names`, `process-order`, `process-tab`, `review-filter`, `schedules`, `sidebar`, `safepoint.dev.*`).

Run reads and source reads are written once: keeping an id that is kept leaves the first and answers it (a read's id is its time and a hash of what was read, so the same id is the same read), as the file written again used to give the same read. The `reads` row needs its `processes` row, which `ensureProcess` (`server/db/scope.ts`) makes until something seeds that table. "Latest" for a source's reads is the last id in byte order, as the last file name was; `source_reads_latest` (migration `0002`) serves `order by read_id collate "C" desc`, since the primary key's order follows the server's collation, which is not byte order everywhere. A kept body that no longer fits its schema is named (`StoredFileError`), except where a page may fall back to the captured copy (`latestSummary`).

A proposal is a new row each time one is made, and "the proposal for a run key" is the latest by `proposed_at` (`keptProposal`: `order by proposed_at desc limit 1`, which the unique index `proposals_by_run_key` serves with no sort; `proposals.test.ts` holds the plan). The apply path compares `proposal.at` with the decisions' `proposedAt`, and Propose shows the current one, so both read the latest; the earlier ones stay as history and nothing reads them yet. Keeping the whole (`keepProposal`) and removing its part is one transaction. A part is replaced after each batch (an upsert on its key, `server/storage/answer-parts.ts`) and reads as none kept when it no longer fits its schema, being a head start only; a database that cannot be read is reported, as it is for reads. A cross-check is an upsert on its key and reads as none kept when its body no longer fits (it is worked out again on demand), a database failure being reported. Records come back in the order they were kept (`json`; `proposals.test.ts` keeps keys whose sorted order differs). `crossCheck()` still drops its part before the caller keeps the cross-check, as with the files.

A write's record is a row per write, as each array entry was, and "the record for a run key" is the latest by `id` (`applications_by_run_key`); a row points at the proposal it wrote (`proposal_id`, found by the proposal's own time, as the apply path matches the decisions' `proposedAt`) and at the read under `readProcessOf`. `run_id` is the kept run a write was made through, and null for one whose decisions came in the request (and for every imported one). A row reads back as the record it was, field for field and in the schema's order; a key the schema does not name survives inside a `json` column (`changes`, `decisions`), but a top-level one has no column, and the import refuses an entry with one. A row whose JSON no longer fits is reported naming its run (`The kept write <process>/<read>.<fp> does not fit the stored shape`); `lastWrite`, for the Outputs page, reads only columns and the length of `changes`, so it stays tolerant. How a write is kept safe across instances is below ("One standing write, settled once").

Learned model limits are one row per model, written per model (`saveKeptLimits`) so an instance learning of one model does not undo another's of another. `lib/definitions/limits.ts` reads them once per process through `limitsReady()`, awaited in `takeSlot` (every paced request), in `withModels` (every choice of a model) and in the `modelLimits.get` procedure; its `state()` throws if asked before that, so a path that misses it fails loudly. A failure to read or write is not an error: the learning starts afresh and is tried again at the next request. A request is counted as `used_count + 1` in one statement (`countRequest`), and the count it returns is the one held after, so instances sharing a model add to one count; learning a limit writes each field only where it is newer than what is kept (by when it was learned), and the day's count only goes up within a day, so a late or older write does not undo another instance's.

## Runs, decisions and instruction versions, as built

Batch 5a built the server side (`server/storage/instructions.ts`, `runs.ts`, `decisions.ts`, `server/operations/record-decisions.ts`, the `instructions`, `runs` and `decisions` routers, and the kept-run path of `application.*`); the screens moved onto them in batch 5b ([Runs on the server](RUNS-ON-THE-SERVER.md), which also records what was done), and `application.*` now takes only a kept run. `safepoint.live-runs.v1` is no longer read or written except to say once that a process's earlier runs are not shown, and to remove that process's entry when the notice is dismissed; `safepoint.instructions.v2`'s published versions are likewise only offered as drafts. The processes the server keeps anything for are listed once, in `server/operations/kept-processes.ts`: every process's instruction versions, and runs only for the two Brunch orders processes.

**Instruction versions.** A process's declared versions are inserted on first need, before anything reads or refers to one (`ensureDeclared`: `insert … on conflict do nothing`, safe when requests arrive together, then each declared label checked to be kept with its own text, a mismatch said rather than papered over); a declared version's `published_at` is the day its label states, `published_by` its declared author. Publishing normalises the text exactly as the instructions panel does before it compares or publishes (`normalisedInstructions` in `lib/process/instruction-diff.ts`: each paragraph trimmed, one blank line between; every declared text is already in that form, and a test holds it), hashes it with `hashOf` (SHA-256 of the UTF-8 bytes, the first twelve hex digits, which the table's check repeats in SQL with `convert_to(text, 'UTF8')`; a test holds the two equal on every declared text, accents, an emoji, a non-breaking space and trailing whitespace, and the text back byte for byte), and answers text that is already a version, of either origin, with that version (`created: false`). Text with a NUL or half a surrogate pair is refused as input: Postgres cannot keep the one, and UTF-8 cannot say the other, so the two sides could not hash it alike. The label is the highest `v<N>` of the process plus one, assigned in one transaction under `pg_advisory_xact_lock` on the process, so two publishes at once take one after the other and get two consecutive labels; the unique key on `(process, version)` holds it besides. `published_by` is `ctx.actor`, null until sign-in.

**Runs.** The server names a run, `run-<uuid>`, and starts it at its process's first step after the instructions, status `running`. Migration `0006` fits the table to what a run is: `read_process`, with the read's key on `(read_process, read_id)` as proposals have it, since the direct process takes reads kept under `brunch-orders`; the key into `rulebook_revisions` dropped, since that table was empty until rulebooks moved (still absent after phase 6: "Rulebooks and profiles, as built"), with a check that the pin has a fingerprint's shape; a check on the id; and `discarded_at`. A run's read may be replaced (a read taken again), its pin set and cleared (moving to the current rules), its stage and status moved; what it started with never changes, and it is never removed (`0007`). Discarding sets `discarded_at` once: the list leaves the run out, its decisions and any write stay, and it moves no further, though what it wrote may still be undone. The list is one query on `runs_by_start`, joined to the version's label, with no bodies. Two starts at once are two runs.

**Decisions.** An event per decision, on the exact proposal row current for the run's key when it is made, which the client names by the proposal's own time as the write does; one made on an earlier proposal is refused in the write's words. The current decision is the latest event per record for the run and proposal (`distinct on (record_key) … order by record_key, id desc`, served by `record_decisions_by_proposal`), a withdrawal meaning none. Events are appended in a transaction under a transaction-scoped advisory lock on the run key (`lockRunKey`): an event that says what the record's current decision already says is not appended, so a decision sent twice, at once or one after the other, is one event; and a decision is refused while a write of the run key is in flight (its lease live). A write through a kept run reads the decisions, prepares, then claims under the same lock only if they are still what it read, so a decision landing between the two makes it give the write up unwritten ("A decision was changed while this write was being prepared…") rather than write decisions the server no longer holds. With each event the server keeps the verdict and checks it worked out: the proposal's, as a person reviews it (`asReviewed`), for an approval or a rejection; `checkProposal` on the values for a change. `actor` is `ctx.actor`.

**The write by kept run** takes the run's text, read and pin from the database, and its current decisions on the current proposal, then goes through the same preparation, checks and claim as a write whose decisions came in the request; the row records `run_id`. The request's own decisions (`proposedAt`, `decisions`) keep working until 5b, marked as going away.

## Importing what is kept on disk

```sh
pnpm db:import             # copies data/ into the database the app would open
pnpm db:import -- --dry-run
```

`scripts/import-kept-data.ts` reads the files the server kept before it kept them in tables (the ones `server/storage/kept-data.test.ts` walks), through the same schemas, from `SAFEPOINT_DATA_DIR` or `data/` under the working directory. It inserts what the table lacks, counts a row already there with the same content as present, and reports (exit 1) one there with other content, a file that does not fit its schema or whose name is not its read's id, and a limit the columns cannot hold; nothing is overwritten and no file is written, moved or deleted. It prints, per kind, files found, rows inserted, present and refused. Run reads, source reads, model limits, proposals, proposal parts, cross-checks, cross-check parts, proposal progress, draft progress and applications are imported, in that order (`KINDS` in `scripts/import-kept-data/kinds.ts`). An applied file is a row per entry, in order, each pointing at the proposal row its `proposedAt` names (proposals go first; a dry run counts the proposals it would insert). An entry already at its place among the run key's rows with the same content is present; one with other content is refused with every entry after it, since the order is the record. A file with two standing entries (pending, verified or mismatch), which the partial unique index cannot hold, is refused whole, with why, never forced; so is an entry holding a key the table has no column for, or a time not written as `toISOString` writes one. A pending entry is imported pending with no lease, and the app settles it when it can read the sheet. The owner's data held one applied file of one entry, verified: imported as one row, and present on a second run. A proposal, cross-check or part is refused if its read is not in `reads` under `readProcessOf` (reads go first, and a dry run counts the reads it would insert; the tables refuse the row too), if the file is not named `<read>.<fingerprint>.json` for the run key it says, or if it fits no schema. A progress file kept as `running: true` is from a process that is gone: it is imported as running under the holder `import`, its lease last renewed when the file was written (no later than two leases ago), so the app reads it as interrupted and a start takes the key over; the file's time stands for `started_at` of every progress row. A model-limits row the app has since updated reads as different; import before the app runs. The scripts load the app's modules through `scripts/resolve-aliases.mjs` (`--import`), which resolves `@/` and extensionless imports as the bundler does.

## Bodies are `json`, not `jsonb`

PostgreSQL's `jsonb` "does not preserve the order of object keys" (manual, 8.14); `json` keeps the input text exactly. `server/db/round-trip.test.ts` holds this against all 14 files under `fixtures/brunch-orders/rulebooks/`, `fixtures/brunch-orders/profile/` and `e2e/fixtures/`: as `jsonb` every one comes back reordered (shorter keys first, then by byte); as `json` every one comes back to the byte. Read through its Zod schema, a `jsonb` body happens to come back exact for every rulebook, profile and index kept today, because Zod rebuilds an object in its schema's order and those files were arranged that way. It is luck, not design: a record's keys (`z.record`) keep `jsonb`'s order, so a proposal's records lose the read's order, and an example setting two fields (as the conformance process's do) no longer round-trips; the test shows both.

So every body is `json`, and the export to `fixtures/` the plan depends on is possible: the test imports both rulebook folders and the profile folder into their tables, exports them, and gets every file back byte for byte, every id reproduced from its body. Times are `timestamptz` read as `Date`, which gives back the files' ISO strings at millisecond precision. What `json` costs: no equality operator, no GIN index, slower `->>`. Nothing queries inside a body; where a column repeats a body's field (an id, a hash, a run key) a check holds them equal.

## What the database enforces, and what is left to code

The database: every key and uniqueness above; a run never removed, what it started with never changed, and a discarded run moved no further (`0007`); a row written once in `instruction_versions`, `reads`, `source_reads`, `data_profiles`, `rulebook_revisions`, `proposals`, `record_decisions` and `rule_decisions` (a trigger refuses update and delete); an instruction version's hash is its text's; a revision's parent, head and profile exist; columns agree with the body fields they repeat; every update of `current_rulebooks` or `current_profiles` moves `revision` on by one, whatever the statement set; at most one pending or written application per run key (a partial unique index); an application's written content never changes, its status moves only forward (pending to verified, mismatch or failed; verified or mismatch to undone), undone has its time, a lease names its holder and its time together, and it is never removed; closed sets of values, as checks; a running job names its holder and lease; deletes of what anything points at are refused.

Code: a revision's id is `fingerprintOf(body)` and a profile's `profileFingerprint(body)` (SQL cannot repeat `JSON.stringify`), checked on write, on read and when seeding; every body is read and written through its Zod schema; the head moves in the same transaction as the revision it names, and a new revision's parent is the head read under the lock below; a run's proposal and its decisions share its run key (`runKeyOfKept`); the current decision is the latest per run, proposal and record, a withdrawal meaning none; a decision is checked against its proposal (the record is in it, a change's values pass `valueProblems`, nothing a blocking check stops) and kept with the verdict and checks the server works out; a published version's text is normalised (`normalisedInstructions`) before it is hashed; a job's lease is renewed and judged.

## Replacing `inTurn` and the job map

`inTurn` (once in `server/storage/files.ts`) and the job map serialised within one process. With several instances:

`inTurn` is gone (phase 6), and the job map with it (7b); each of their uses is now as below.

- **`updateSet`, `updateProfile`**: compare-and-set on `revision`: read, apply the pure change, `update … where revision = $seen`, and on no row read again and retry, five times in all, then refuse ("These rules kept changing while your change was being kept: look at them again and try once more."). No lock is held while the change is worked out, it works through the pooler, and the change functions are pure. `saveSet` and `saveProfile` replace by design: an upsert.
- **`putRevision`**: one transaction under `pg_advisory_xact_lock` on the process and instructions hash: read the head, insert the revision `on conflict do nothing`, and if it was new, move the head. An advisory lock because the head row may not exist yet, so there is nothing to lock with `for update`; transaction-scoped because Neon's pooler cannot hold a session lock.
- **`applyDecisions`, `undoApplication`, settling**: as built in the next section.
- **Parts, cross-checks, model limits**: single-statement upserts; a count is `used_count + 1` in the statement.
- **Jobs**, as built (`server/jobs/run-job.ts`, batch 7b): the work of a draft, a rewrite of one rule and a proposal is a Vercel Workflow run (`server/workflows/`), whose steps are its units of model work (the find, each rule written, the batches still to propose, each batch, the keeping of the whole) and whose kept step results let a run that a restart or a redeploy interrupted carry on from the last finished step. The row is still the progress the screens read; the run's steps write it. Starting claims the key with `insert … on conflict do update … where not running or (run_id is null and heartbeat_at < now() - 60 s) or run_id = <the run seen to be over> returning`: a row back means this start holds the key, under a fresh `holder` (a random id of the claim, not of a process), with `run_id` null; none, that a job is running under it, whose progress is answered. Before the upsert the start asks the run named on a running row how it stands, so a row whose run has ended or is gone can be claimed over, while a live one cannot; the upsert's own `where` keeps the decision atomic. The claimant then starts the workflow with `start(…, { experimental_hook: { token } })`, the token being the key: Workflow admits a run and its token in one step and refuses a second live run under it (`HookConflictError`, naming the owner), so two claims that both got through (one abandoned and taken over, then late) still make one run; the start records the run, its own or the owner, as `run_id … where holder = <its claim>`. A claim that has recorded no run after `LEASE_MS` (60 s, by the database's clock) was abandoned between the claim and the start, and may be taken over. A step writes `where holder = <the claim it was started under> or run_id = <its run>` and fills `run_id` if the start could not, so a run that lost the key cannot write over the one that has it. `jobProgress` takes a running row written in the last 10 s at its word; otherwise it asks the run's status, and reads `pending` or `running` as running, and `completed`, `failed`, `cancelled` or a run the World no longer knows, while the row still says running, as interrupted in the words of the kind (a World that cannot be asked cannot say it stopped, so that reads as running). `heartbeat_at` is now when the row was claimed or last written; no timer renews it. Each step is handed ids (the job's key, the claim, the read, the instructions' hash, the rules' fingerprint, the model chosen), reads what it works on from the tables, and may run twice: a find this draft already kept (`foundAt` at or after the start) is taken as it is; a rule is written only while it is as it was when the job began (found blank, or for a rewrite as recorded at the start); a batch asks only for records the part in `answer_parts` does not answer; the whole proposal is kept at the instant the run chose, and found rather than kept twice. A step does not retry what its work throws (that would ask the models again for the same failure): it hands the message back and the run ends the job with it, as the job's error was before. Every model of the chain spent until within 15 minutes is the one wait the run takes on (a `RetryableError` whose `retryAfter` is when the first is back); per-minute pacing and short per-minute waits stay in the step (`lib/definitions/limits.ts`), and a day's limit is still said to the person. Draft progress is `(process, 'drafts', <instructions hash>)` and proposal progress `(process, 'proposals', '<read>:<fingerprint>')`; a draft's `writing` and a proposal's live `activity` are columns, written at most every two seconds, one write after another. A second start answers the row's progress; `startDraft`, `startRewrite` and `startProposal` return a promise, and a read that does not fit is refused at once. Under Vitest the directives are not compiled, so `server/workflows/runner.ts` calls the workflow in the test's process with the same one-run-per-token contract, and a test's stand-in models are held for the claim (`stand-ins.ts`). What is still safe only by assumption: a step's model calls and writes are not fenced by the claim, only its progress notes are; on Vercel a step that outlives its function (`maxDuration: 'max'`, the plan's ceiling, at most 800 s) is run again from its start, and an inline step whose invocation died is taken up again only after Workflow's inline ownership lease (`WORKFLOW_INLINE_OWNERSHIP_LEASE_SECONDS`, 860 s); the learned model limits' in-process state (who is resting, which requests went this minute) is per instance, so a step on another instance learns a refusal afresh.

## Rulebooks and profiles, as built

Phase 6. `server/storage/rulebooks.ts` keeps its exported functions and their meaning (`loadSet`, `saveSet`, `updateSet`, `putRevision`, `loadRevision`, `listRevisions`, `headOf`, `loadProfile`, `saveProfile`, `putProfile`, `loadConfirmedProfile`, `ownerFor`, `ownerToDraft`), and adds `updateProfile`, the compare-and-set change of the profile under review that the `rules.profileColumn` and `rules.confirmProfile` procedures now use in place of a read and a save. Every body is parsed through its schema on the way in and out; a body that does not fit, a revision whose body is not its `fingerprintOf` and a profile whose body is not its `profileFingerprint` are reported (`StoredSetError`), never read as "nothing kept".

**Instructions first.** A rulebook belongs to a kept version of its instructions (`current_rulebooks_instructions_fk`). The first call for a process makes sure of its declared versions (`ensureDeclared`), so a declared text is always kept; a published one is kept when it is published. `saveSet` and `putRevision` refuse a rulebook for instructions that are not kept ("These instructions are not a kept version: publish them before keeping rules for them."). In the app the text always comes from a run, which is under a kept version, so this is not met there; tests keep their own text first (`keepText`, `findKept` in `lib/definitions/set.fixture.ts`).

**Rule decisions.** Each act on a rule is a `rule_decisions` row in the same transaction as the change it makes, with `ctx.actor`: `confirm_intent`; `accept`, with the refusal where code did not take it; `deny`, with the note; `choose`, with the version; `applies_to`, with the reading; each with the definition as it was before the change and the rulebook's `revision` it was read at. And `confirm_profile`, when `updateProfile` moves the profile under review from unconfirmed to confirmed (once, not again on a second press). A decision on a definition the rulebook does not have is not recorded, as it changes nothing. The body keeps its stamps: the fingerprint reads `approvedAt`.

**Seeding from `fixtures/`.** `server/storage/rulebook-files.ts` is the only code that reads or writes a rulebook or profile file. On the first call for a process in a server process (`oncePerDatabase` in `client.ts`, forgotten on a failure so the next call fails as loudly), it reads `fixtures/<process>/` under the working directory and checks every file before it writes anything: it fits its schema; it is byte for byte what the export would write; each revision's id is `fingerprintOf` its body and each profile's `profileFingerprint`; every body names the folder's instructions hash; `revisions.json` lists each `<id>.json` there, once, each parent before its child, the head among them, every time as `toISOString` writes one; and the folder's `<version>-<hash>` is a kept instruction version with that label. Any difference fails, naming the file. Then, in one transaction under `pg_advisory_xact_lock` on the process, it inserts with `on conflict do nothing`: the confirmed profiles, the profile under review, and per folder the current rulebook, each revision in the index's order and the head.

The rule for a database that already holds state: **insert what it lacks, never overwrite**. A current rulebook, a head or a profile under review the database holds stays; a revision or confirmed profile is written once and named by its content, so one already there is kept as it is. Chosen because the database is where people decide and `fixtures/` is a copy that lags it: overwriting on start would silently undo decisions made since the last export, and refusing to start on any difference would make every unexported decision a fault. So a rulebook accepted in the database but not yet exported survives someone pulling new fixtures: it stays current and head; revisions the pulled files add that it lacks are inserted beside it (a second child of a shared parent, where both moved on), and the next export writes the database's state over the pulled files, where the diff shows the difference for a person to settle. A folder naming a version the database does not keep (one published in another database, whose text is not in the repository) refuses to seed, naming the folder.

**The export.** `pnpm rulebooks:export` opens the database the app would (not while `pnpm dev` holds `data/pglite/`), seeds each process that has rulebooks or a profile in `fixtures/`, and writes every process's rulebooks and profiles back in the present layout: `<version>-<hash>/` from `instruction_versions`, `current.json`, `<id>.json` per revision, `revisions.json` in `seq` order with the head, and `profile/current.json` and `<id>.json`, each as `writeKept` writes it. `-- --to <folder>` writes elsewhere; files the database does not hold are left alone. Bytes could differ in three places, each ruled out: key order (bodies are `json`, and seeding refuses a file not already in the schema's order), times (`revisions.json` times pass through `timestamptz` at millisecond precision, and seeding refuses one `toISOString` would write differently) and the folder's label (taken from `instruction_versions`, which seeding holds equal to the folder's). `rulebook-files.test.ts` seeds a scratch database from the real `fixtures/`, exports into a scratch folder and compares all ten files byte for byte.

**The run's pin is not yet a key.** `runs_rulebook_fk` (a run's `rulebook_id` a revision kept for its own process and instructions) holds for every pin the app makes: Calculate keeps the revision it calculates on under the run's own instructions (`putRevision`, reason `used`) before the screen pins it. It was restored and then taken out again, because the browser tests break it: they serve the frozen rulebook in `e2e/fixtures/` (accepted under instructions v2) to a run the real server starts under v3, so the pin names a revision kept for other instructions, the server refuses it, and Propose, which opens once the server has the pin, never does. Restoring it needs those tests to serve a rulebook kept for the run's instructions, and the key added `NOT VALID` (migrating comes before seeding, so a database that kept runs before this phase holds pins it gets the revisions of only when seeded). Until then the pin keeps its shape check only. A reset database (`pnpm db:reset`) is seeded again at the first request after the server starts; a server left running across a reset does not notice until it restarts.

## One standing write, settled once

As built (`server/storage/applications.ts`, its statements in `application-rows.ts`). No lock or transaction is held across a call to the sheet; each step is one statement whose `WHERE` says what must still be true, so of two callers one changes the row and the other matches nothing and reads the row again.

- **The claim.** A write first settles what it can of the latest record and prepares (reading the sheet), then inserts its `pending` row: the record, kept before anything changes the sheet. The partial unique index `applications_one_standing` refuses it while another write of the run key stands, whoever made that one since this caller looked, and the refusal is answered as the record found says (below). A row that cannot be inserted means nothing is written.
- **The lease.** The pending row carries a lease: `holder`, a random token of this one call (not of the process: two requests in one process are two holders), and `heartbeat_at`, set by the database's clock, renewed every 15 s by a timer of its own while the call works (`HEARTBEAT_MS`) and lapsed 60 s after the last renewal (`LEASE_MS`), judged in SQL with `now()`, so instances whose clocks differ agree. Before each change to the sheet (adding the resource, writing the block) the writer renews it `where holder = <token>`: a writer that no longer holds its row writes nothing. Settling, finishing an undo or leaving a write pending gives the lease back, and so does the call's `finally`, so a record a call left unsettled is settled at the next look rather than a minute later.
- **Telling a write in flight from one whose process died.** A row whose lease is live is in flight: no one but its holder settles it, so a block not yet written is never read as a write that failed. A caller that finds it is refused in new words (below), and a preview shows it pending. A row whose lease has lapsed, or was given back, belongs to no one, and the next caller that can read the block settles it (`landed`: `after` verified, `before` failed, else mismatch; an unreadable block leaves it pending). A process that dies mid-write leaves a live lease for at most 60 s, during which the run reads as "still being made".
- **Settling** is `update … where id = $1 and status = 'pending' and (holder = <token> or the lease has lapsed)`. Of a writer and a previewer settling one lapsed row at once, both read the same block and reach the same outcome; one update wins, and the other reads the row again and answers with what it holds, so the outcome is that of either order.
- **The writer finds its row settled by someone else.** That happens only once its lease lapsed while it was still working (its renewals did not reach the database for 45 s or more). It never writes over the row. If the row says failed (a settler read `before`) and the writer's own read-back says the write landed, the writer keeps the write again as a new row with what it read back: the unique index lets it in, since failed does not stand, and it becomes the latest, so undo still restores the cells it replaced and no retry is let in over it. If another write of the run has begun since, the index refuses that row and the writer says so ("This write landed after it was recorded as failed, and another write of this run began since. Check the <tab> <resource> by hand."). Otherwise it answers with the row as kept.
- **Undo** reads the latest record (settling it), checks that the block still holds `after`, and claims by marking `undo_started_at` with a lease, `where status in ('verified', 'mismatch') and undo_started_at is null` and no lease is live: of two undos one marks, the other is refused, and the sheet is written back once. While the mark's lease is live a settler leaves it (the block may still hold `after` though the undo is about to land); once it lapses, the block holding `before` makes it `undone`, and `after` clears the mark. An undo that finds its mark cleared by such a settler but has read back `before` records `undone` all the same (a forward move), unless another undo has marked it since. A write while an undo is in flight is refused, and so is an undo while a write is in flight.
- **New words a person may see**: "The last write to the <tab> <resource> is still being made. Try again in a moment." (a write or an undo while another write is in flight) and "The last write to the <tab> <resource> is being undone. Try again in a moment." (a write or an undo while an undo is in flight), from `stillWriting` and `beingUndone` in `lib/definitions/apply.ts`; and the error above.
- **Every transition the code makes, against the guard** (`0005`): pending to verified, mismatch or failed, its error set or cleared; pending to pending with its error and lease changed; verified or mismatch with the mark and lease set, renewed or cleared; verified or mismatch to undone with `undone_at`; a retry after failed or undone is a new row. Each is allowed; none changes what was written or moves back. The trigger and the index are exercised on the storage code's own paths (`applications-instances.test.ts`), not only in `schema.test.ts`.
- **Still safe only by assumption.** The lease assumes that a writer whose sheet call is in flight keeps renewing: a writer cut off from the database, but not from the sheet, for over 45 s can have its row settled as failed under it. It then keeps the write again as above, or, if a retry began in that window, says so for a person to check. The sheet calls (`lib/sheets/composio.ts`) have no timeout of their own. Tests drive every interleaving through two loads of the module that share only the database, holding calls to the in-memory sheet (`sheet.fixture.ts`, `hold`) and setting a heartbeat back to stand for a lease running out.

## Model attempts, as built

The engine reports each model call through what it is given and never imports the server: `withModels` in `lib/definitions/calls.ts`, which every request passes, takes a `Recording` (`lib/definitions/attempts.ts`) beside its call, and `find`, `write` (through `Asking.record`), `proposeBatch`, `crossCheckBatch` and `advise` pass one when their caller gave them a `record`. With none, the call is made exactly as before. Each model asked is one attempt; a model passed over because it is resting is not asked and not recorded. Requests and tokens are tallied by a middleware wrapped round the model only when recording, and pacing's waits and retries (`limits.ts`) through an `AsyncLocalStorage` scope of the call. The server's recorder (`attemptRecorder`, `server/storage/model-attempts.ts`) adds what the call was part of and numbers attempts from 1 per purpose and definition. The draft and proposal jobs supply one (`server/jobs/draft.ts`, `proposal.ts`), as do the `calculate.crossCheck` and `rules.advise` procedures. A row is inserted without the call waiting for it, and a failed insert is let go; a job awaits `settled()` once its work ends, and a procedure before it answers, so the rows are written before the job is reported done or the reply leaves (milliseconds, after the model's own seconds), and tests can rely on that.

Outcomes, the table's set unchanged: `answered`; `refused` (the caller's checks sent the answer back: find's accounting, a write not passing its checks, no proposal submitted, a cross-check not covering every record once, advice quoting what is not in the instructions); `quota` (a 429); `busy` (5xx, or too slow); `failed` (anything else, a call cut short included). Every row has the process, purpose, model, job kind and key, run (null: the jobs are named by run key, not by a kept run), instructions hash, read, fingerprint and definition where known, attempt, start, duration, outcome, input, output and thinking tokens as the provider reports them, requests, `waited_ms`, and the first line of any error (200 characters at most). `asked` and `answer`, per purpose:

| Purpose       | Context                                          | `asked`                                                          | `answer`                                                        |
| ------------- | ------------------------------------------------ | ---------------------------------------------------------------- | --------------------------------------------------------------- |
| `find`        | job `drafts`, instructions, read                 | prompt and system sizes, sentences, problems it was re-asked on  | definition ids found, checks, sentences accounted for, problems |
| `write`       | job `drafts`, instructions, read, definition     | prompt and system sizes, earlier definitions                     | checked, problems left, kept, shape kind, unfit reason, blocked |
| `propose`     | job `proposals`, instructions, read, fingerprint | the batch's record keys, checks                                  | records submitted, problems left                                |
| `cross-check` | instructions, read, fingerprint                  | prompt and system sizes, the batch's record keys, values to work | records answered, values agreeing, problems                     |
| `advise`      | instructions, read, definition                   | prompt and system sizes, versions, whether asked again           | the verdict                                                     |

No prompt, answer, formula, value, reason or quote is kept. Nothing reads the table yet; the debug drawers on the Rules step (`rules-debug.tsx`) are its natural reader.
