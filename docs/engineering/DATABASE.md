# Database

Status: designed and migrated; in use for a run's reads, a source's reads and learned model limits (batch 4a) and for proposals, cross-checks, their partial answers and job progress (batch 4b), not yet for the rest. Written 14 November 2026. `server/db/` holds the client, the schema and its tests; `drizzle/` holds the migrations. Those kinds are read and written through `database()` with no file fallback; the other storage functions in `server/storage/` still keep files, and the next phases move them onto these tables, keeping their signatures. With no `DATABASE_URL` the app opens PGlite under `data/pglite/` on the first request that needs it; tests use `inScratchDatabase()`, and `database()` refuses a test that has not set one up.

## Opening it

`database()` in `server/db/client.ts` is the only way in. It chooses once per server process, holds the result on `globalThis` (as `server/jobs/run-job.ts` holds the job map), and connects only when first asked:

| Where          | Driver                                                        | Why                                                                                                                                                                                                                  |
| -------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL` | node-postgres `Pool`, 5 connections, idle 10 s, timeout 10 s  | Interactive transactions need a connection; Fluid compute reuses an instance. Use Neon's pooled URL (`-pooler`). Each setting's reason is in `poolFor`.                                                              |
| No URL         | PGlite on disk, `data/pglite/`, migrated on first use         | The app starts with no credentials (the README's promise, CI's browser job). A development dependency, loaded by dynamic import only on this path.                                                                   |
| Tests          | PGlite in memory, one per test file (`inScratchDatabase()`)   | No network, no files. Migrated once per test file and emptied before each test (`truncate … restart identity`): about 10 ms, against 150 ms to copy a migrated one (`clone()`) and 600 ms to create and migrate one. |
| Browser tests  | PGlite under `data/pglite-e2e/`, cleared as the server starts | `playwright.config.ts` starts `pnpm dev` with `DATABASE_URL` and `DATABASE_URL_UNPOOLED` empty and `SAFEPOINT_PGLITE_DIR=data/pglite-e2e`. See below.                                                                |

`SAFEPOINT_PGLITE_DIR` moves the PGlite folder (relative to the working directory); `driverFor` takes an empty URL as none, as `||` does. The browser tests' server gets both URLs empty because Next does not take a variable that is already set, an empty one included, from `.env.local` (`@next/env` uses a file's value only where the starting environment has none; checked with an empty `DATABASE_URL` and a `.env.local` naming one), so a developer's remote `DATABASE_URL` never meets a test row; and it gets a folder of its own, so a run does not write into the developer's `data/pglite/`. The server's start command removes that folder, so each run begins empty. `reuseExistingServer` is on outside CI: a server already on the port is used as it is, whatever database it has, and only the one the config starts is kept off a remote database.

Opened on the first request that asks, not at start: creating and migrating `data/pglite/` measured about 1.5 s (reopening it 0.7 s) including Node's own start, against 30 s browser-test timeouts, and requests arriving together share one open (`database()` stores the promise before awaiting it; `client.test.ts` holds it). The first request of a fresh `pnpm dev` took about 5 s, mostly the route's compile.

Storage functions take a `Database`, which a Drizzle transaction also is, so a caller can run one inside its own `db.transaction(...)`. Plain SQL's result type depends on the driver; prefer the query builder.

```sh
pnpm db:generate   # a migration from server/db/schema.ts; review the SQL, commit it
pnpm db:migrate    # applies drizzle/ to DATABASE_URL_UNPOOLED, DATABASE_URL, or data/pglite
pnpm db:reset      # drops everything and migrates; refuses any target not marked (below)
pnpm db:studio     # migrates, then browses it; not while pnpm dev holds data/pglite
```

Migrations run over the direct connection (`DATABASE_URL_UNPOOLED`): Neon's pooler is PgBouncer in transaction mode, which a migration's session state does not survive. In production they are to run in the Vercel build, production only; that step is not wired yet. `db:reset` refuses on Vercel and under `NODE_ENV=production`, and on any server unless `SAFEPOINT_RESETTABLE_DATABASE_URL` is that exact URL. Every module in `server/` begins with `import 'server-only'`, which throws outside a React server build; the scripts run Node and drizzle-kit with `--conditions=react-server`, under which the package resolves to its empty module, as Vitest's alias does.

`drizzle/0000_tables.sql` is generated. `drizzle/0002_source_reads_latest.sql` adds the one index a query needed beyond the keys. `drizzle/0001_guards.sql` is written by hand (`drizzle-kit generate --custom`): drizzle-kit cannot write functions or triggers and keeps no record of them, so regenerating neither drops nor repeats it, and `server/db/schema.test.ts` fails if a guard is missing.

## Tables

Every table carries its scope: `process` (a key into `processes`), except `source_reads` (by `source`: a source knows no process) and `model_limits` (a quota is the API key's). A future workspace or session is an attribute of a `processes` row, not a column on every key: a process belongs to one workspace, the same template in two workspaces is two process ids, and no key or foreign key changes.

| Table                  | Holds                                                                                          | Key                                                                   |
| ---------------------- | ---------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `processes`            | The scope                                                                                      | `id`                                                                  |
| `instruction_versions` | Each version's text, label, note, who and when; written once                                   | `(process, hash)`; `version` unique; `hash` checked against the text  |
| `reads`                | A run's read, whole; written once                                                              | `(process, id)`                                                       |
| `source_reads`         | A source's own read, every resource; written once                                              | `(source, read_id)`                                                   |
| `data_profiles`        | Each confirmed profile; written once                                                           | `(process, id)`, the `profileFingerprint`                             |
| `current_profiles`     | The profile under review, with a compare-and-set `revision`                                    | `process`                                                             |
| `current_rulebooks`    | The rulebook under review per instructions, with a compare-and-set `revision`                  | `(process, instructions_hash)`                                        |
| `rulebook_revisions`   | Each accepted rulebook: body, parent, reason, time, shape version, note, profile; written once | `(process, instructions_hash, id)`, the `fingerprintOf`; `seq` orders |
| `rulebook_heads`       | The revision in use per instructions                                                           | `(process, instructions_hash)`                                        |
| `runs`                 | Instructions, read and pinned revision (each a foreign key), stage, status, trigger, who, when | `(process, id)`                                                       |
| `proposals`            | Each proposal made, whole, by run key; written once; the latest by `proposed_at` is in use     | `id`; `(process, read_id, fingerprint, proposed_at)` unique           |
| `cross_checks`         | The model's cross-check by run key; replaced on a new check                                    | `(process, read_id, fingerprint)`                                     |
| `answer_parts`         | A proposal or cross-check still being answered (the old `.part` files); replaced per batch     | `(process, kind, read_id, fingerprint)`                               |
| `record_decisions`     | Approve, change (with values), reject or withdraw, on one record of one proposal, in one run   | `id`; appended only                                                   |
| `rule_decisions`       | Confirm intent, accept, deny (note), choose (version), applies to, confirm profile             | `id`; appended only                                                   |
| `applications`         | A write and its undo: status, range, before, after, changes, decisions, undo marker            | `id`; one standing per run key                                        |
| `jobs`                 | A job's progress as columns, its holder and lease                                              | `(process, kind, key)`                                                |
| `model_limits`         | Per model: shared quota, learned limits, today's count                                         | `model`                                                               |
| `model_attempts`       | One model call: purpose, model, what it was part of, outcome, duration, tokens, asked, answer  | `id`                                                                  |

Every foreign key restricts deletes; nothing cascades. A decision points at the exact proposal row it was made on, and a rule decision keeps the definition as it was shown and the rulebook's `revision` it was read at, so what was approved stays readable after the rulebook moves on. A profile's and a rulebook's `read_id` are not keys: the reads they came from are run data, and a database seeded from `fixtures/` has none. Nor is the `read_id` of a proposal, a cross-check or a part (migration `0003` dropped those three foreign keys): Brunch orders' direct process (`brunch-orders-direct`) proposes on reads kept under `brunch-orders`, which is where every read is kept, so `(process, read_id)` names no row of `reads` for it, and 4 of the 8 proposals in the owner's data are its. Reads are never deleted, and the only way in (`runProcedure`) takes a read that is kept; the import refuses a proposal whose read is in no process's `reads`. A later phase that keys `runs` to `reads` meets the same case and must decide whose reads a process uses. A proposal's fingerprint is not a key either: a process with no rulebook proposes under the empty rulebook's (`noRules`).

Stay in the browser: `safepoint.instructions.v2`'s unpublished `draft`, and the preferences and previews (`assistant`, `calculate-revealed`, `inputs`, `last-process`, `process-names`, `process-order`, `process-tab`, `review-filter`, `schedules`, `sidebar`, `safepoint.dev.*`).

Run reads and source reads are written once: keeping an id that is kept leaves the first and answers it (a read's id is its time and a hash of what was read, so the same id is the same read), as the file written again used to give the same read. The `reads` row needs its `processes` row, which `ensureProcess` (`server/db/scope.ts`) makes until something seeds that table. "Latest" for a source's reads is the last id in byte order, as the last file name was; `source_reads_latest` (migration `0002`) serves `order by read_id collate "C" desc`, since the primary key's order follows the server's collation, which is not byte order everywhere. A kept body that no longer fits its schema is named (`StoredFileError`), except where a page may fall back to the captured copy (`latestSummary`).

A proposal is a new row each time one is made, and "the proposal for a run key" is the latest by `proposed_at` (`keptProposal`: `order by proposed_at desc limit 1`, which the unique index `proposals_by_run_key` serves with no sort; `proposals.test.ts` holds the plan). The apply path compares `proposal.at` with the decisions' `proposedAt`, and Propose shows the current one, so both read the latest; the earlier ones stay as history and nothing reads them yet. Keeping the whole (`keepProposal`) and removing its part is one transaction. A part is replaced after each batch (an upsert on its key, `server/storage/answer-parts.ts`) and reads as none kept when it no longer fits its schema, being a head start only; a database that cannot be read is reported, as it is for reads. A cross-check is an upsert on its key and reads as none kept when its body no longer fits (it is worked out again on demand), a database failure being reported. Records come back in the order they were kept (`json`; `proposals.test.ts` keeps keys whose sorted order differs). `crossCheck()` still drops its part before the caller keeps the cross-check, as with the files.

Learned model limits are one row per model, written per model (`saveKeptLimits`) so an instance learning of one model does not undo another's of another. `lib/definitions/limits.ts` reads them once per process through `limitsReady()`, awaited in `takeSlot` (every paced request), in `withModels` (every choice of a model) and in the `modelLimits.get` procedure; its `state()` throws if asked before that, so a path that misses it fails loudly. A failure to read or write is not an error: the learning starts afresh and is tried again at the next request. The day's count is still this process's own number written back, not `used_count + 1` in the statement, so two instances sharing a model undercount until that is done.

## Importing what is kept on disk

```sh
pnpm db:import             # copies data/ into the database the app would open
pnpm db:import -- --dry-run
```

`scripts/import-kept-data.ts` reads the files the server kept before it kept them in tables (the ones `server/storage/kept-data.test.ts` walks), through the same schemas, from `SAFEPOINT_DATA_DIR` or `data/` under the working directory. It inserts what the table lacks, counts a row already there with the same content as present, and reports (exit 1) one there with other content, a file that does not fit its schema or whose name is not its read's id, and a limit the columns cannot hold; nothing is overwritten and no file is written, moved or deleted. It prints, per kind, files found, rows inserted, present and refused. Run reads, source reads, model limits, proposals, proposal parts, cross-checks, cross-check parts, proposal progress and draft progress are imported, in that order; a later batch adds its kind to `KINDS` in `scripts/import-kept-data/kinds.ts`. A proposal, cross-check or part is refused if its read is in no process's `reads` (reads go first, and a dry run counts the reads it would insert), if the file is not named `<read>.<fingerprint>.json` for the run key it says, or if it fits no schema. A progress file kept as `running: true` is from a process that is gone: it is imported as running under the holder `import`, its lease last renewed when the file was written (no later than two leases ago), so the app reads it as interrupted and a start takes the key over; the file's time stands for `started_at` of every progress row. A model-limits row the app has since updated reads as different; import before the app runs. The scripts load the app's modules through `scripts/resolve-aliases.mjs` (`--import`), which resolves `@/` and extensionless imports as the bundler does.

## Bodies are `json`, not `jsonb`

PostgreSQL's `jsonb` "does not preserve the order of object keys" (manual, 8.14); `json` keeps the input text exactly. `server/db/round-trip.test.ts` holds this against all 14 files under `fixtures/brunch-orders/rulebooks/`, `fixtures/brunch-orders/profile/` and `e2e/fixtures/`: as `jsonb` every one comes back reordered (shorter keys first, then by byte); as `json` every one comes back to the byte. Read through its Zod schema, a `jsonb` body happens to come back exact for every rulebook, profile and index kept today, because Zod rebuilds an object in its schema's order and those files were arranged that way. It is luck, not design: a record's keys (`z.record`) keep `jsonb`'s order, so a proposal's records lose the read's order, and an example setting two fields (as the conformance process's do) no longer round-trips; the test shows both.

So every body is `json`, and the export to `fixtures/` the plan depends on is possible: the test imports both rulebook folders and the profile folder into their tables, exports them, and gets every file back byte for byte, every id reproduced from its body. Times are `timestamptz` read as `Date`, which gives back the files' ISO strings at millisecond precision. What `json` costs: no equality operator, no GIN index, slower `->>`. Nothing queries inside a body; where a column repeats a body's field (an id, a hash, a run key) a check holds them equal.

## What the database enforces, and what is left to code

The database: every key and uniqueness above; a row written once in `instruction_versions`, `reads`, `source_reads`, `data_profiles`, `rulebook_revisions`, `proposals`, `record_decisions` and `rule_decisions` (a trigger refuses update and delete); an instruction version's hash is its text's; a revision's parent, head and profile exist; columns agree with the body fields they repeat; every update of `current_rulebooks` or `current_profiles` moves `revision` on by one, whatever the statement set; at most one pending or written application per run key (a partial unique index); an application's written content never changes, its status moves only forward (pending to verified, mismatch or failed; verified or mismatch to undone), undone has its time, and it is never removed; closed sets of values, as checks; a running job names its holder and lease; deletes of what anything points at are refused.

Code: a revision's id is `fingerprintOf(body)` and a profile's `profileFingerprint(body)` (SQL cannot repeat `JSON.stringify`); every body is read and written through its Zod schema; the head moves in the same transaction as the revision it names, and a new revision's parent is the head read under the lock below; a run's proposal and its decisions share its run key; the current decision is the latest per run, proposal and record, a withdrawal meaning none; a job's lease is renewed and judged.

## Replacing `inTurn` and the job map

`inTurn` (`server/storage/files.ts`) and the job map serialise within one process. With several instances:

- **`updateSet`, a profile under review**: compare-and-set on `revision`: read, apply the pure change, `update … where revision = $seen`, and on no row read again and retry, a few times. No lock is held, it works through the pooler, and the change functions are already pure. `saveSet` replaces by design: an upsert.
- **`putRevision`**: one transaction under `pg_advisory_xact_lock` on the process and instructions hash: read the head, insert the revision `on conflict do nothing`, and if it was new, move the head. An advisory lock because the head row may not exist yet, so there is nothing to lock with `for update`; transaction-scoped because Neon's pooler cannot hold a session lock.
- **`applyDecisions`, `undoApplication`, settling**: no lock across the call to the sheet, which can take seconds on a pooled connection. Inserting the pending row is the claim (the unique index refuses a second); settling is `update … where id = $1 and status = 'pending'`; an undo claims with `undo_started_at` where it is null and finishes where it is still that value. A refused claim is answered as today's "already written" or "not read back".
- **Parts, cross-checks, model limits**: single-statement upserts; a count is `used_count + 1` in the statement (model limits do not yet: see above).
- **Jobs**, as built (`server/jobs/run-job.ts`): the holder is one id per server process (`holderId()`: pid and a UUID, held on `globalThis` with the job map). Starting claims the key with `insert … on conflict do update … where not running or holder = <this process> or heartbeat_at < now() - 60 s returning`: a row back means this process holds the job and runs it, none that another process holds it on a live lease. The lease is judged by the database's clock, so instances whose clocks differ agree. The holder renews `heartbeat_at` every 15 s on a timer of its own (`HEARTBEAT_MS`, `LEASE_MS`; unref'd, cleared when the job ends), not with the notes, so a model call of minutes cannot let it lapse; each note renews it too. Notes are written one after another, each as the job stands, and only `where holder = <this process>`, so a process that lost its lease cannot overwrite the one that took the job over. A failed claim, note or renewal never stops the job: it runs held in memory, and a job whose last note could not be kept stays answered from memory. A second start in the same process gets the running job's object, as before. A second start while another process holds the job on a live lease gets a copy of the progress that process has kept (`running: true`), nothing of it held here; the screens' polling then reads the row through `jobProgress`, which says running while the lease is live and, once it has run out, interrupted in the words of the kind. `startJob`, and so `startDraft`, `startRewrite` and `startProposal`, return a promise (the claim is a query); a read that does not fit is still refused at once, not by the promise. Draft progress is `(process, 'drafts', <instructions hash>)` and proposal progress `(process, 'proposals', '<read>:<fingerprint>')`; a draft's `writing` and a proposal's live `activity` are columns, written at most every two seconds, as the file was, and `writing` reads back as `null` where a proposal's file had none. What is still safe only within one process: the in-memory map answers while a job runs here, and what the work itself does (model calls, writes to a sheet) is not fenced by the lease, so a process that lost it while still running goes on to the end; a job's work is never resumed after a restart, it is reported interrupted and a person starts it again.

## Open questions for the owner

1. **Order of the move.** The proposal's review (13 November) puts rulebooks last, after runs, decisions and writes. The schema carries both; the export test shows `fixtures/` can stay the reviewed copy. Which phase moves rulebooks?
2. **Instruction text before a rulebook.** `current_rulebooks` and `rulebook_revisions` require the instructions version to be kept. `saveSet` and `putRevision` receive the set, not the text, so the text must be kept where it is in hand (drafting, publishing). Acceptable, or relax the key?
3. **Version labels** are unique per process. Two browsers can each publish a `v4` today; on the server the number must be assigned there.
4. **Keeping everything.** Reads, proposals and decisions are never deleted. Is there a retention limit, and should model answers in `model_attempts`, which hold the sheet's data, have one?
5. **Decisions per run or per run key.** Two runs on one read and rulebook share a proposal and a standing write today. Decisions are designed per run; the write stays per run key.
6. **Background work on Vercel.** A job started without `after()` or Workflow may be frozen with its instance. `@vercel/functions`' `attachDatabasePool` releases idle connections before suspension; it is not installed.
7. **The reset mark.** An exact-URL environment variable; a branch made from `main` copies data, so the guard cannot live in the database. Enough?

Unverified until the Neon project exists: the lease's timer and its database-clock expiry across instances, the pool over a real pooled URL, `pg_advisory_xact_lock` through Neon's pooler, `drop schema public` under Neon's owner role in `db:reset`, and pg's warning about `sslmode=require` in Neon's URLs.
