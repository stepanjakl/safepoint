Status: built. ## What a run is, as the client has it today

`useRunSelectionState` (`components/app-shell/runs/run-selection.tsx`) starts a live run for a process with a live thread (`brunch-orders`, `brunch-orders-direct`): id `run-<Date.now()>`, `status: 'running'`, `trigger: 'manual'`, `counts: { items: 0 }`, `instructionsVersion` the current label, and `data.additionalInstructions` when the start control was given a note. It is added to `safepoint.live-runs.v1` (`live-runs-store.ts`) and selected. Nothing ever changes `run` after that: the status stays `running` and the counts stay 0. Everything that moves is merged into `data` by `updateLive`:

| `data` key  | Set by                                                                                              | Holds                                                                                                                               |
| ----------- | --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `read`      | `ReadStep` (`orders-run.tsx`), by hand in the rulebook run, at once (`automatic`) in the direct run | `RunRead`: the read's id and summary (time, source, title, url, tab ids, tab row counts, problems). A read taken again replaces it. |
| `rules`     | `RulesStep`                                                                                         | `RulesProgress`: approved, total, intent confirmed                                                                                  |
| `calculate` | `CalculateStep`                                                                                     | `CalculateProgress`: the rulebook fingerprint it calculated on (the pin), agreed, total, checked                                    |
| `propose`   | `ProposeStep`                                                                                       | `ProposeProgress`: fingerprint, `proposedAt`, running, total, need-you and writes counts, and `decisions` (`Record<key, Decision>`) |
| `apply`     | `ApplyStep`                                                                                         | `ApplyProgress`: the write's status                                                                                                 |

`onMoveRules` (Propose's "use the current rules") clears `calculate` and `propose`, so the pin goes and Calculate runs again on the current rules. "Discard this run" (`removeLive`) deletes the entry from the browser, whatever it wrote. The stage shown is worked out in render (`latest` in `OrdersRun` and `DirectOrdersRun`); it is not kept.

The direct process differs: it has no Rules or Calculate step, reads the live sheet as the run opens, proposes at once, and works under the empty rulebook of its instructions (`noRules(text)`), so it never pins one.

On the server (`runs`): the id is the server's; `instructions_hash` names a kept `instruction_versions` row; `read_id` is set by `runs.record` and may be replaced; `rulebook_id` is the pin (rulebook process only), cleared with `rulebook: null`; `stage` is the step the screen shows as latest, `status` is one of `running`, `awaiting_review`, `approved`, `completed`; `discarded_at` marks a discarded run, which the list leaves out and which moves no further. Decisions are `record_decisions` events; rules, calculate, propose and apply progress are not kept, but worked out from what they summarise (table below).

## Procedures

Every procedure is gated as before (`gatedProcedure`: local development only) and is told who is acting (`ctx.actor`, `actorOf` in `server/api/trpc.ts`: null until sign-in exists). A refusal reaches the screen as a tRPC error with the code shown and the message in a person's words; an input that does not fit is `BAD_REQUEST`, "Invalid request.". `process` is a process whose runs are kept (`brunch-orders`, `brunch-orders-direct`), except for `instructions.*`, which take any process (`promotion-release`, `support-handoff` too). `runId` is the id the server gave.

### `decisions`

The proposal is the current one for the run's key (process, read, rulebook fingerprint), named by its own time, `proposedAt`, as Apply names it. Every answer is `{ kind: 'decisions', proposal: { id, at } \| null, decisions }` with `decisions` in the proposal's record order, each `{ kind: 'approve' \| 'change' \| 'reject', values (a change's, else null), verdict, checks, actor, at }`; a mutation answers `{ kind: 'stale', … }` instead when the pinned rulebook no longer fits the read, as Propose's procedures do.

The server works out the verdict and checks kept with each event: an approval or rejection keeps the record's as the proposal has them (with no rulebook, a record the model was unsure of reads `decide`: `asReviewed` in `lib/definitions/propose.ts`, the same rule as `asReviewed` in `propose-step.tsx`, which should import it); a change keeps `checkProposal` on its values. The browser's `verdict` and `checks` on a `Decision` are no longer sent. A decision the record already has (same kind and values, or a withdrawal of nothing) is not kept again, so a double press or a retry leaves one event.

### `application`, by kept run

`application.preview`, `application.write` and `application.undo` take, besides their existing inputs, `{ process, runId }` (`write`: plus `acknowledged`). By kept run the server reads the run's text, read and pin, the current proposal for its key and the run's current decisions on it; the rest is the existing path, shared (`decidedOf`, then `opened`, in `server/api/routers/apply.ts`). New refusals by kept run: the run ones above (a discarded run may still `undo`, and nothing else); "These decisions were made on an earlier proposal. Decide on the current one." (`BAD_GATEWAY`, as on the old path) when the run decided only on an earlier proposal; and, from `write`, a preview whose problem is "A decision was changed while this write was being prepared. Look at the decisions again and write." when a decision landed after the write read them. Undecided records are prepareWrite's own "Not decided yet: <keys>." A write by kept run records `applications.run_id`.

Two things the client does differently today and should stop doing: it lists a process's declared versions in declaration order (`[...previous, current]`, which is v2, v1, v3 for Brunch orders); the server lists by number. And it lets a person publish the text of an earlier version as a new label (Restore, then publish); the server answers that version (`created: false`), so the panel should say "That is v1" and select it rather than announce a v4.

## Query keys and cache updates

Follow `rules-step.tsx` and `propose-step.tsx`: a mutation's answer is written into the query it answers (`queryClient.setQueryData(query.queryKey, answer)`), so the screen changes once, focus stays on the control that was pressed, and nothing refetches. The query client's defaults (`components/trpc/provider.tsx`: `staleTime: 30 s`, no retry) stand.

| Query                                   | Key from                                           | Written by                                                                                                                                               | Invalidated by                                                                                                                                                                                  |
| --------------------------------------- | -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `instructions.list({ process })`        | `trpc.instructions.list.queryOptions({ process })` | `instructions.publish`: when `created`, append `version` and set `next` to the number after it; when not, leave the list and select the version answered | Nothing else; another tab's publish is seen at the next mount or after `staleTime`                                                                                                              |
| `runs.list({ process })`                | `trpc.runs.list.queryOptions({ process })`         | `runs.start` (prepend the run), `runs.record` (replace the run by id), `runs.discard` (remove it)                                                        | —                                                                                                                                                                                               |
| `runs.get({ process, runId })`          | `trpc.runs.get.queryOptions(...)`                  | `runs.start` (seed it: the answer plus the text the screen started with), `runs.record`, `runs.discard` (merge, keeping `instructions.text`)             | —                                                                                                                                                                                               |
| `decisions.current({ process, runId })` | `trpc.decisions.current.queryOptions(...)`         | `decisions.record`, `recordMany`, `withdraw` when the answer is `kind: 'decisions'`                                                                      | A new proposal: when `propose.get`'s `proposal.at` differs from `decisions.current`'s `proposal.at`; a refusal in the earlier-proposal words; `runs.record` that changes `readId` or `rulebook` |
| `application.*`                         | mutations, as now                                  | —                                                                                                                                                        | `ApplyStep` asks a preview again when the decisions change: key its effect on the `at` of each current decision rather than on the decisions object it is passed                                |

`propose.get` keeps `staleTime: 0, gcTime: 0` and its polling. Write `runs.record({ stage, status })` from an effect on what the thread works out, only when it differs from the kept run's, so a render never sends one. Keep `retry: false` on every mutation: a decision is safe to send twice, a write is not.

## A run's identity and selection

The server names a run (`run-<uuid>`); the browser never makes an id again. `start` becomes `await runs.start(...)`, then select `answer.id`. The address keeps `?run=<id>` (`useRunSelectionState` already writes it), so a link to a run now opens it in any browser. An id the server does not keep (an old `run-<ms>`, or a mistyped one) answers `NOT_FOUND` from `runs.get`: select nothing and drop `?run=`, as a page arrived at without one does. The page server components (`app/(shell)/examples/brunch-orders/page.tsx`, `…-direct/page.tsx`) pass `initialRunId` through unchanged; they could also prefetch `runs.list`.

`useLiveRuns`, `LiveRun`, `updateLive`, `removeLive` and `live-runs-store.ts` go. `safepoint.live-runs.v1` is no longer read or written; following the `safepoint.<thing>.v<N>` convention in `AGENTS.md`, `instructions-store.ts` moves its draft to `safepoint.instructions.v3` holding `{ [process]: { draft } }` only, reading a v2 draft once into it so unpublished work is not lost. Do not reuse a removed key for another shape.

## Earlier browser-only runs, and tabs open when it lands

What `localStorage` held is not imported: those runs and decisions were never a trustworthy record. Say so once, where it would be missed:

- In the runs list of a process whose `safepoint.live-runs.v1` entry is non-empty: "Runs started before today were kept only in this browser and are not shown. Anything they wrote to the sheet is still there, with its record." with a control that dismisses it; dismissing removes the key's entry for that process (the one write of the old key, then it is gone).
- In the instructions panel, where `safepoint.instructions.v2` holds published versions: "Versions published in this browser were kept only here. Publish one again to keep it." and offer each one's text as a draft.

A tab open when the change lands runs the old code until it is reloaded: it still reads and writes `localStorage`, and its writes still work while the old `application.*` inputs exist (below). After a reload its `?run=run-<ms>` is not kept, so the page opens on nothing with the notice above. That is why the old inputs are removed one step after the screens move, not with them.

## Order of work and the browser tests

Each step is shippable alone. The browser tests run against one dev server and one database for all workers (`playwright.config.ts`, `data/pglite-e2e/` cleared as it starts), so a test that starts real runs sees other tests' runs in `runs.list`. Either serve `runs.*` and `decisions.*` from an in-memory stand-in per page through `mockProcedure` (`e2e/trpc.ts`), a small `e2e/kept-runs.ts` that answers `start`, `list`, `get`, `record`, `discard` and the decisions as the server would; or let them reach the test server and select rows by the id `runs.start` answered, never by position. The first suits the specs that already mock everything after the read; the second suits `brunch-orders.spec.ts`, which reads through the real server.

1. **Instructions from the server.** `useInstructions` reads `instructions.list`; `publish` calls `instructions.publish`; the draft moves to `safepoint.instructions.v3`. Covers: `e2e/process-panels.spec.ts` (it seeds `safepoint.instructions.v2` published versions in "review numbers follow the draft…": seed them by `instructions.publish` from the test, or mock `instructions.list`), `e2e/rulebook-transitions.spec.ts` (writes `instructions.v2` mid-test and fires `safepoint:instructions`: replace with a mocked `instructions.list` answer and a refetch), `e2e/run-selection.spec.ts` (boundaries between versions), `e2e/brunch-orders*.spec.ts` (each run shows its version's text).
2. **Runs from the server.** `useRunSelectionState` lists with `runs.list`, starts with `runs.start`, selects by the answered id, discards with `runs.discard`; the threads read the run from `runs.get` and record `readId` and the pin with `runs.record`; text comes from `runs.get`'s `instructions.text`. Covers: `e2e/brunch-orders.spec.ts` (start, read, discard), `e2e/brunch-orders-rules.spec.ts`, `-calculate.spec.ts`, `-profile.spec.ts` (each starts a run), `e2e/run-transitions.spec.ts` (seeds two `live-runs.v1` runs: mock `runs.list` with two kept runs), `e2e/run-selection.spec.ts` (the placeholder processes are untouched: they play a recorded run), `e2e/process-menu.spec.ts` and `e2e/process-panels.spec.ts` (the sidebar and tabs around a selected run).
3. **Decisions from the server.** `ProposeStep` reads `decisions.current` and decides through `decisions.record`, `recordMany` and `withdraw`; `ApplyStep` and the threads work out "all decided" from it. Covers: `e2e/brunch-orders-propose.spec.ts` (every decision, the filter, approve all ready, undo, and the write): mock `decisions.*` beside the `propose.*` it already mocks.
4. **The write from the server.** `ApplyStep` sends `{ process, runId }` (and `acknowledged`) to `application.preview`, `write` and `undo`. Covers: `e2e/brunch-orders-propose.spec.ts` ("a person decides every record, then writes what Apply shows and can undo it": its `application.preview` mock reads `body.decisions` today; read the mocked decisions store instead).
5. **The notices** for earlier browser-only runs and versions, then removing `live-runs-store.ts`. Covers: a new case in `e2e/run-selection.spec.ts` or `brunch-orders.spec.ts` seeding `safepoint.live-runs.v1` and checking the notice and its dismissal.
6. **Remove the old inputs** (next section), in a release after step 4. Covers: `server/api/routers/apply.test.ts`, whose old-path cases move to the kept-run path (`kept-run.fixture.ts` has the arrangement).

`e2e/brunch-orders.spec.ts:13` fails before and after this batch (`label-content-name-mismatch`); it is not this work's.

## Inputs that go away

In `server/api/routers/apply.ts`, marked "GOING AWAY (5b)": the second member of each `z.union`: `text`, `readId`, `rulebook`, `evaluation`, `proposedAt` and `decisions` on `preview` and `write`, and `text`, `readId`, `rulebook`, `evaluation` on `undo`; then `decidedOf`'s branch for them, `keptProposal`'s use there, and `keptRunProcedure`'s branch for a run named by its fields once no procedure takes one (`runProcedure` stays for `propose.*`, `calculate.*` and `rules.*`, which still name a run by its fields; moving those onto `{ process, runId }` is the same change and can follow). `toSend` in `apply-step.tsx` goes with them.

## Not decided

- **Who moves `status`.** Today nothing does. The table and `runs.record` take `running`, `awaiting_review`, `approved` and `completed`; a natural mapping is running until a proposal exists, awaiting review while a record is undecided, approved once all are decided, completed once written and read back (or nothing to write). The server could work this out itself from proposals, decisions and applications instead of being told; that wants a decision on whether the list should then compute it per row (a join on three tables) or keep it as a column moved on each event. Left to the screens for now, as the simplest that cannot be wrong about what the screen shows.
- **Counts in the list.** A row's tally (`items`, `blocked`, `needsDecision`) needs the proposal body; the list loads none. Either keep the counts on the run when a proposal is made and decided, or leave live rows at `{ items: 0 }` as today.
- **A read's summary by id.** `read.get` returns the whole read; a `read.summary({ id })` with exactly `RunRead`'s fields would spare the card the tab values. Not added, since nothing calls it yet.
- **`model_attempts.run_id`** is still null: the jobs that make model calls (`server/jobs/draft.ts`, `proposal.ts`) are named by run key, not run. Pass the run id once the screens start jobs from a kept run.
- **A declared label published first.** If a later release declares `v5` in code and a person has already published a `v5` here, `ensureDeclared` refuses with "<process> declares instructions v5, but v5 is kept with other text." rather than renumber either. Declaring a version means choosing a label the server has not given; how to choose it (the next label at release time, or declared versions living outside `v<N>`) is for the owner.
- **Two runs on one run key share a write.** Decisions are per run, the write per run key (owner's decision): two runs on the same read and rulebook decide separately, and whichever writes first stands; the other's preview then says "This run has already written to the Orders tab. Undo that first to write again." The screens should say which run wrote it (`applications.run_id`).

## What was done

Batch 5b, in the six steps above, one commit each. Where it differs from what the sections above specify:

- **Runs are read from the list, not from `runs.get`.** `runs.list` holds every field a thread needs but the text of the instructions, and that comes from `instructions.list` by label, so selecting a run asks the server for nothing more and a switch between two runs never shows the empty page while a run loads. `runs.get` is not called by the screens. An id in the address that is not in the list selects nothing and is dropped, after the list is asked once more in case the run was started elsewhere since it was read. A discarded run is not in the list, so its link opens nothing.
- **`read.summary` was added.** A run keeps a read's id, and its card (time, source, tabs, rows, problems) used to be kept in the browser. `read.summary({ id })` answers what `read.keep` answers for a read already kept, without the tabs' values, so a run that comes back to its read does not load the whole sheet to show a card. Tested in `server/api/routers/read.test.ts`. `read.keep`'s answer is written into it, so a read just taken needs no second request.
- **`status` and `stage` are not recorded.** As decided: nothing moves `status`, and the screens go on working out the step they show. `runs.record` is called for `readId` and the rulebook pin only.
- **Propose opens on the server's pin.** `canPropose` asks that the run has a pin, not that Calculate reported one this session, so a run whose pinned rules no longer fit the read still opens at Propose and says so there, as it did.
- **How far Rules, Calculate, Propose and Apply have got is held in the thread for the headings only**, filled by each step's own query as it opens. The decisions it reports are only those the server holds.
- **`asReviewed` could not be imported by the screen from `lib/definitions/propose.ts`** (that file loads the model calls and the limits' database reader). It moved to `lib/definitions/reviewed.ts`, which both read.
- **Decisions show at once and are taken back if refused** (optimistic, requests one after another through a mutation scope), where the hand-over only said the cache is written from the answer. The reasons are in `propose-step.tsx`.
- **The two notices, and `live-runs-store.ts`.** The store was removed with the move of the runs (step 2), since nothing reads it; the notice reads the old key itself (`earlier-runs.ts`) and its dismissal removes that process's entry. The instructions notice offers each earlier version as a draft, and its dismissal empties the old key's `published`, keeping its `draft`.
- **Publishing text that is already a version** says "That is v3. These instructions are already published, so no new version was made." with a button that opens it (the draft is dropped then), instead of announcing a new label.
- **The old `application.*` inputs went in step 6**, with `decidedOf`'s branch for them, `keptProposal`'s use there and `keptRunProcedure`'s branch for a run named by its fields (`runProcedure` stays for `propose.*`, `calculate.*` and `rules.*`). `apply.test.ts` arranges a kept run with its decisions.
- **Browser tests.** Instructions and runs reach the real test server and its shared database, and a test selects what it started by the id the server gave (`e2e/kept-runs.ts`; a run row carries `data-run-id`). `e2e/kept-instructions.ts` serves `instructions.list` for a test that needs versions already published without keeping any, `e2e/kept-decisions.ts` stands in for `decisions.*` where a test serves its own proposal, and `e2e/runs-in-a-second-browser.spec.ts` runs a run and a decision through the real server and shows both in a fresh browser context. No model runs in a test, so that proposal is kept for the run by a development-only route (`app/api/dev/test-proposal`), the one thing a test does to the database that a screen cannot.
- **Not done**: the counts in the runs list (live rows count nothing, as before), `model_attempts.run_id`, and a label for a declared version a person published first (all as decided).
