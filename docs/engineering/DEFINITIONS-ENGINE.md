# Definitions engine

Status: current code guide for `lib/definitions/`, checked in November 2026. It is used by [Brunch orders](../processes/brunch-orders/PLAN.md). The earlier Brunch weekend engine it grew out of is [archived](../archive/BRUNCH-WEEKEND-ENGINE-GUIDE.md).

## Contract

A process supplies a `DefinitionProcess`: its ID and a `DefinitionSubject` with the records, lookups, typed columns, proposal fields and reader words. Brunch orders declares this in `lib/processes/brunch-orders/process.ts`; the engine does not hard-code products or orders. The current read joins Products, Stock, Sales and Deliveries by product key and looks up Parameters by category. A process may also declare timing columns (`DataShape.timing`): hours since a weekday and time last came round, and hours until a deadline in the week being planned, both worked out from when the data was read, never the wall clock.

One definition has a name, the exact instructions text it interprets, a `check` or `number` result, optional check consequence, quoted constants and groups, a formula, and examples. A formula may read the current record, proposal fields and earlier definitions. `lib/definitions/types.ts` validates the saved set.

A number's formula is written by the model. A check's is not: the model fills in one of five fixed shapes (`shape-schema.ts`), and code writes both the formula and the sentence a person approves from it (`shapes.ts`), so the two cannot say different things. The shapes are limit, step, only when, target and flag (flag only for a check a person decides), each optionally limited to a group or to conditions. What a blank cell means is not the model's to say: it is a fact about the data, kept on the data profile (below); a shape stored before that keeps its own `if_blank` and its formula exactly. Conditions are joined by "and" only. Names in a shape are short references (`column:<column>`, `value:<id>`, `constant:<id>`, `proposed:<field>`, `moment:<moment>`, `hours_since:<moment>`); a bare name is read where only one thing could be meant, and so is a name under the wrong kind (`column:<earlier value>`), a field written `proposed:<field>`, a missing field where the process has only one, and a group of `null`. For a check that stops a proposal, code lets a proposal of nothing through wherever the process declares what nothing is (a proposal field's `none`). Time is said only with moments (`DataShape.timing.moments`), each a weekday and time column pair that is observed, a deadline or the next occurrence, compared before or after one another, the period's start or the read; `hours_since` reads only an observed moment. A shape never sees the signed hours worked out for formulas, so it has no sign to get wrong. A rule no shape can say is refused, naming why (it needs "or", other arithmetic, or data that is not there), and a person rephrases it. Checks accepted before shapes keep their formulas and still run.

## Data profile

A read's column types used to be inferred afresh from each read, so one decimal stock count or one column blank throughout made an accepted rulebook fail to type-check. A data profile (`profile.ts`) fixes them. `profileOf` proposes one from a read: one entry per column a formula can reach, named as a shape names it (`<column>`, `<lookup>.<column>`), typed as the process declares (`DataShape.types`) or else from every non-blank cell (whole numbers, decimals, real checkboxes as yes/no, otherwise text; null for a column blank throughout), with a label, whether blanks were seen, and what a blank means for a rule (`blank`: skip, fail, or null until answered). A person confirms it; every change (`setColumnType`, `setColumnLabel`, `setColumnBlank`) gives a new id and clears the confirmation. Profiles are kept in `fixtures/<process>/profile/`: `current.json` under review, `<profile id>.json` for each confirmed one, written once (`saveProfile`, `putProfile`, `loadProfile`, `loadConfirmedProfile`). A set records the confirmed profile it was drafted on (`profileId`), and the rulebook fingerprint includes it; a set without one reads as before. `withProfile` gives the process with its data held to a profile, so every `owner.subject.data` reads it; `ownerFor` loads the one a set names, `profiledFor` refuses a set whose profile was not loaded, and a draft starts on the kept profile only once confirmed (`ownerToDraft`). Against a profile, `records.ts` keeps each column's type whatever the read holds: a cell that does not fit is a read problem by its cell, a whole number in a decimal column is a decimal, a column blank throughout stays typed, a column the profile lists that the read lacks is a problem, and so is a declared type that disagrees with the profile; a column the profile does not list is typed from the read.

A check's shape no longer says what a blank cell means. Each column it reads takes the profile's answer: skip columns form the leading guard (the rule does not apply, and Propose says so), fail columns and unanswered ones must be present for the rule to hold, and with no profile every column fails. A moment is skipped only where both its columns say skip; the start and the read are never blank. The sentence says each meaning where the read has such a blank. Accept refuses a rule reading a column with blanks whose meaning is unanswered (`unansweredBlanks`), naming it. Once the profile is changed and confirmed again, `rebaseSet` moves the rulebook under review onto it: it writes each such check's formula again from its shape, versions included, reviews every definition again on the read, compares its versions again, and withdraws acceptance only from what changed or no longer passes and what reads it. Revisions are never touched.

## From instructions to acceptance

1. The development read route loads a captured or live five-tab read and keeps it under an ID. `records.ts` reports missing tabs, bad keys and invalid typed cells.
2. `find.ts` identifies definitions from one instructions version. It accounts for every sentence as a quantity's working, a check or only context, and code refuses an answer that leaves one out, points at a definition it did not list, or lists one no sentence states; one more try is allowed, then the draft stops and nothing is replaced. The account is kept on the set (`accounting`), and the review shows what was read as context. `draft.ts` starts a server-side draft and records progress; `write.ts` writes each definition in order.
3. `formulas.ts` type-checks and evaluates CEL. `checks.ts` tests the definition against its read, quoted constants and groups, dependencies and worked examples. A formula must read the data and everything it declares, and a check's examples must show it holding and failing wherever the read lets it do both. The model's check tool uses these checks.
4. The person confirms the intent and accepts or denies each definition. `decide.ts` reruns the full review against the read before acceptance. A denial can carry a note for the next write.
5. `store.ts` reads saved sets through the schema and writes a temporary file before renaming it over the old set. Each instructions version has a folder, `fixtures/<process>/rulebooks/<version>-<instructions-hash>/`, found by the hash: `current.json` is the rulebook under review, and `<rulebook id>.json` is a revision: an accepted rulebook, written once and never again. The id is a fingerprint of what was accepted (`fingerprintOf`). `revisions.json` records each revision's parent, reason (`accepted` when the decision that completes the rulebook is made, `migrated` when a script rewrites it, `used` when a run first uses one never frozen), time and stored-shape version, and the head. Revisions are reached only through `putRevision`, `loadRevision`, `listRevisions` and `headOf`, so a database can replace the files without the engine changing.
6. `calculate.ts` works every accepted calculation out for every record, and has the model cross-check them; cross-checks are kept in `data/<process>/cross-checks/`.
7. `propose.ts` has the model propose values for every record, trying them against the accepted checks (`try_proposals`) before it submits. Code checks every proposed value again (`checkProposal`), verifies every cited cell, and keeps its own verdicts: ready, decide, blocked, or unchecked where the rulebook has no check to run. A record the model leaves is checked with each field at its declared `none`; a calculation that cannot be worked out on a record fails every check that needs it on that record, by name, and leaves the rest running; a value below a field's declared `min` blocks. Proposals are kept in `data/<process>/proposals/`; a person's decisions on them belong to the run. A check written "not in scope, or the rule" (its outermost `||` led by a negation that reads no proposal field) does not apply to a record out of scope: it holds, its working stops at the guard, and Propose says "Doesn't apply".
8. `fits.ts` type-checks a revision against the read it is used on, as Accept does, without the examples. A revision is kept as it was accepted, so one written before a column's type changed is refused on use, naming each definition that no longer fits, and the run is offered the current rules when they fit.

9. `apply.ts` writes a decided proposal to the output the process declares, through an `OutputSheet` it is given. It reads the sheet again, refuses a write if a data tab has changed, runs every check again at that moment, reads the block back, and keeps the record in `data/<process>/applied/`. A record left as it is is checked on the sheet as read now, though nothing is written for it. Undo restores the block only while it holds what was written.

`app/api/dev/brunch-orders/rules/route.ts` exposes get, draft, intent, write and decide actions for this development flow; `calculate/route.ts`, `propose/route.ts` and `apply/route.ts` beside it do the same for those steps. None is a public process-definition API. The [development log](../processes/brunch-orders/DEVELOPMENT-LOG.md) records why its checks and approval boundary changed.

`debug.ts` says what code finds of a draft without asking any model, for the debug drawers on the Rules step (`components/brunch-orders/rules-debug.tsx`): each thing `reviewBreakdown` holds a definition to, run again and shown together, and what its formula gives on every record at a value a person tries. The values offered are the proposal's own fields the formula reads, with the process's words for them, so the drawers know no process. They also list the columns each rule reads, itself and through the calculations it reads, and those no rule reads, counting the columns a worked-out column comes from as read. A wrong reading can pass every check and agree with all the data when a column happens to be 0, so this is for a person to compare: rules about one thing that read different columns. `review` is built from the same parts, so the two cannot disagree. What the model did on each attempt is not recorded yet.

A draft writes each definition twice from the same input (`writeAgreed`), neither write seeing the other. Two checks with the same shape agree; otherwise `differencesBetween` compares how the two behave on every record at a range of values. If they differ, the definition keeps working for what reads it but cannot be accepted until a person chooses a version (`choose`, which takes the version's shape with its formula), shown as the sentence each would check. Accepting a definition with a shape refuses one whose formula is not the one its shape gives. A third write is only for a write that failed the checks or refused: a refusal is never compared, any shape wins over it, and a rule is refused only when every write refuses. After two refusals, a draft with no model chosen writes once more on the drafting model (Flash): its shape is compared with one written before if there is one, and otherwise stands alone, unconfirmed; its refusal stands. A model a person chose is kept throughout. A stored shape keeps only the fields its kind reads, in one spelling (bare field, no group where none was meant, every reference as `kind:name`; `canonicalShape`), and a write keeps only the constants and group the shape names: `check_definition` drops the rest and says so, rather than sending the model back to fix what the shape never reads. Where versions are split, "Which is right?" asks Flash once, or Flash-Lite where Flash is busy or spent (`advise.ts`), which version the instructions support. The answer quotes the instructions, and code checks the quote is really there. It opens in the assistant as advice and is never kept or applied: a third reading of the same words is a vote, and the vote was wrong on 2 of 6 rules, so the person still chooses on the card. The development log has the numbers behind this.

`limits.ts` keeps requests within what Google allows: each request of a tool loop waits for a slot, a per-minute refusal is waited out in place, and a busy model is tried once more, so a loop keeps its progress. Limits are learned from refusals and kept in `data/model-limits.json` for a week; `GEMINI_REQUESTS_PER_MINUTE` overrides them. What cannot be waited out reaches `calls.ts`, which moves to the next model of the family, or stops if all are spent. `app/api/dev/model-limits` reports how a model's quota stands.

## Present limit

Writing has been tested only against a sheet held in memory, and the Brunch orders plan marks history as a later phase. A check sees one record at a time, and proposal fields are whole numbers. A stored accepted set and a captured read are not a durable production review record.
